# 第 78 轮评审（2026-11-01）— 配额是策略，不是约束

r76 的教训是"读后写只有在有数据库约束时才安全"。按这条线索扫了一遍写路径，`加成员`这一条露了出来。

## 1. F-140（P1）先 COUNT 再 INSERT

原来的流程（在 handler 里）：

    inUse := CountMembersByUser(user)
    if quota > 0 && inUse + len(add) > quota { 409 }
    AddMembers(...)   // 另一个事务

计数与插入**不在同一个事务里**。PostgreSQL 的 READ COMMITTED 下，两个并发请求各自读到 `inUse = quota-1`，
都通过检查，都插入——租户就超过了管理员设的上限。SQLite 的单写者又一次把问题挡住了。

## 2. 修法：事务内先取租户行锁

配额是"数量上限"，没法用唯一索引表达（这点和 r76 的单管理员不同）。可移植的做法是**给写者一个串行点**：

    BEGIN
      UPDATE users SET id = id WHERE id = user   -- 空更新取行锁
      SELECT COUNT(*) FROM network_members WHERE user_id = user
      -- 超限则 ROLLBACK 并返回 ErrQuotaExceeded
      INSERT INTO network_members ...
    COMMIT

两个方言都支持"空更新取行锁"；后到的事务在 `UPDATE` 处阻塞，拿到锁时前一事务已提交，于是读到新的计数。

## 3. 为什么保留 handler 里的检查

handler 那句检查现在只是**快速失败 + 友好文案**，真正的把关在 `AddMembersBounded` 里。
两层不是冗余：一层给出 `quota_exceeded` 的语义错误，一层保证不会被并发绕过。

## 4. 验证

| 用例 | 断言 |
|---|---|
| `TestAddMembersBoundedEnforcesTheQuota` | 超限整批拒绝**且一条都没落地**；正好到限通过；再多一个拒绝；`quota=0` 视为不限 |
| `TestConcurrentMemberAddsRespectQuota` | 6 个并发加成员、配额 2，最终成员数不超过 2（SQLite 与 PostgreSQL 都跑） |

负向自测：把事务内的判断短路成 `if false && ...`，第一条用例立刻报 `batch over quota = <nil>`。

## 5. 一个诚实的说明

并发用例本身是**概率性**的——它不一定每次都能踩中窗口。所以真正的证据是那条确定性用例（事务内检查）加负向自测，
并发用例只是补充观察。这一点在 r76 也成立：那里的决定性证据是"索引存在性"断言，不是并发跑。

## 8. 判断

同一类问题这一轮又找到一处。规律很清楚：**凡是"读一个数、据此决定要不要写"，在 PG 上都不安全**，
除非那件事能表达成约束（唯一索引）或者有一个串行点（行锁 / 事务）。
