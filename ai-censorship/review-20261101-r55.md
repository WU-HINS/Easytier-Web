# 第 55 轮评审（2026-11-01）— 阻止接入是单向门

r54 记的是"实现了但没接线"。本轮记它的镜像：**实现了但没暴露**。

## 1. F-111（P1）能阻止，不能看也不能解除

`blocked_devices` 这条链路的每一环都在：

| 层 | 存在吗 |
|---|---|
| 表（user_id + machine_id 主键、尝试计数、最后尝试时间） | 有 |
| `BlockDevice` / `UnblockDevice` / `IsBlocked` / `ListBlockedDevices` | 有 |
| 心跳校验（被阻止的设备拿不到会话） | 有 |
| HTTP 接口 | **只有"删除时顺带阻止"这一个入口** |

也就是说：管理员删设备时勾了"阻止"，从此**看不到这条记录、也没有任何办法撤销**。
想放行只能去改数据库。这不是一个安全特性，是一个永久性误操作陷阱。

## 2. 修复

| 端点 | 行为 |
|---|---|
| `GET /api/v1/machines/blocked` | 列出本租户被阻止的设备（机器 id、主机名、阻止时间、尝试次数、最后尝试时间） |
| `DELETE /api/v1/machines/blocked/{machineID}` | 解除阻止 |

界面：设备页新增"已阻止接入"面板，列出设备与尝试次数，带"解除阻止"按钮。

`TestBlockedDevicesCanBeListedAndLifted` 走完整条链：
用 `DELETE /machines/{id}?block=true` 触发阻止 → `IsBlocked` 为真 → 列表里有它 →
**另一个租户的列表里没有它** → 解除 → `IsBlocked` 为假且列表清空。

跨租户那条断言是顺手加的：阻止记录属于租户，泄露它等于泄露"某人踢过哪台设备"。

## 5. 判断

"实现了但没暴露"和"实现了但没接线"是同一个病的两面：**能力在代码里，但不在系统里**。

到这轮为止，这一类已经被扫出三处：r17（对账循环）、r54（旧库检测）、r55（阻止接入）。
它们的共同特征是：单元层面完整、集成层面缺失——而评审如果只看"函数写得对不对"，永远发现不了。
