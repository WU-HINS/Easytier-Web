# 第 77 轮评审（2026-11-01）— 声明了的索引，引擎里真的建了吗

r76 的 P1 是"单管理员没有数据库约束"。修完之后要问的是：**其余约束呢？**

## 1. F-139（P2）从"一个索引"到"全部索引"

schema 里声明了 13 个索引，其中 4 个是**部分索引**（带 WHERE 谓词）。此前没有任何用例检查它们是否真的建成。

新用例 `TestDeclaredIndexesExistInTheEngine` 的做法：

1. `dsm.Export()` 拿到声明；
2. 逐条向引擎查询定义——SQLite 查 `sqlite_master`，PostgreSQL 查 `pg_indexes`（都限定当前 schema）；
3. 比对三件事：**存在**、**唯一性一致**、**部分谓词还在**。

结果：两个方言各 13 个索引 / 12 张表全绿（SQLite 记的是 `CREATE INDEX ...` 原文，PG 记的是规范化后的 `indexdef`）。

## 2. 负向自测：把谓词拿掉

光"通过"不算证据。把 `IndexDDL` 里拼 WHERE 的那两行临时删掉：

    users.uq_users_single_admin lost its partial predicate "role = 'admin'":
    CREATE UNIQUE INDEX uq_users_single_admin ON users(role)

立刻红。恢复后转绿。

这条负向用例恰好复现了 r76 的成因：**谓词丢了，索引还在，唯一性还在，但语义完全不同**——
没有 WHERE 的话，"role 唯一"意味着只能有一个 user 和一个 admin，系统直接不可用。

## 3. 一个方言差异（值得记下来）

第一次跑 PG 失败：`expected 2 arguments, got 1`——PG 的查询要 `(tablename, indexname)`，
SQLite 只要 `(name)`。改为按方言构造参数后通过。

这不是被测代码的 bug，但它说明**"同一件事在两个方言下接口不同"**是常态，写跨方言断言时不能想当然。

## 6. 判断

r76 修的是**一个**缺失的约束；r77 让"声明与实际不符"这件事**在每一张表、每一个索引上都能被发现**。

这类用例的成本很低（一次遍历 + 一次查询），价值在于：以后新增索引时，声明漏了谓词、方言不支持这种写法、
或 reconciler 跳过了它，都会在门禁里立刻显形。
