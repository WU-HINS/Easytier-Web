# 第 95 轮评审（2026-11-01）— 冒烟里那条永远为真的断言

r94 的结论留了个尾巴：审计覆盖了静态检查和 Go 用例，但**部署走查的断言**没人验证过。
这轮补上——用产品级变异跑完整冒烟，看断言会不会真的拦下来。

## 1. 第一次变异：忽略成员覆盖（断言命中）

在副本里把 `ParseOverrides(member.OverrideConfig)` 改成 `ParseOverrides(nil)`，跑完整冒烟：

    member override set      204
    member override read     {"override_config":"{mtu:1300}"}
    FAIL: the member override never reached the device

**好的结果**：断言按设计拦住了。

（第一次尝试把参数写成空字符串，直接编译失败——那不是证据，是噪声，重做了一次。）

## 2. 第二次变异：不发 stopped 行（F-161，断言没命中）

把 `log.Printf("stopped")` 改成 `"halted"`，跑完整冒烟：

    exit: 0

**冒烟通过了。** 一个进程从来没有记录"干净停止"，走查却说一切正常。

原因在 `grep -q "stopped"`：reconcile 每次都会打印

    reconcile: pushed=0 skipped=0 failed=1 compile_errors=0 stopped=0

——里面就有 `stopped`。断言匹配到的是**计数器**，不是退出日志。

## 3. 修法：锚定整行

两条断言都改成匹配行首时间戳 + 行尾：

    grep -qE "^[0-9]{4}/[0-9]{2}/[0-9]{2} [0-9]{2}:[0-9]{2}:[0-9]{2} stopped$"

再跑同一个变异：

    FAIL: the process did not log a clean stop

未变异的冒烟仍然 26 步全过。

## 4. 这一轮的教训

r92 的教训是"守卫可能什么都没看"，这轮是它的孪生兄弟：
**守卫可能看着一个碰巧包含关键词的无关行。**

| 失效方式 | 例子 |
|---|---|
| 守卫不看（范围错了） | r92：只扫 `.tsx`，`.ts` 一个都没扫 |
| 守卫看错（匹配太松） | r95：`stopped` 匹配到 `stopped=0` |
| 守卫看空（断言在子 shell 里） | r69：断言写在命令替换里，从未执行 |

三种都"显示 PASS"。区别只在于你怎么才能发现它。
