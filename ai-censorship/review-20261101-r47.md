# 第 47 轮评审（2026-11-01）— 把"守卫扫描"变成方法

r46 的结论是"同类'守卫存在但无证据'的地方还能继续找"。本轮把它做成一个可重复的动作。

## 1. F-099（P2）守卫扫描

做法：把 `internal/httpapi/*.go` 里所有 `writeError(...)` 的文案抽出来（66 条），
与测试文件里出现的文本比对，列出"没人断言过"的位置。

第一次跑出来 62 条。**但不能按这个数字干活**——很多守卫是通过状态码断言的（`401` / `403`），
文案没被引用不等于行为没测。于是逐条看"行为有没有被覆盖"，挑出真正空白的：

| 守卫 | 有测试吗 |
|---|---|
| 管理员不可被删除/禁用 | 有（r2 的角色矩阵覆盖了 403/409） |
| 跨站写保护（Origin 校验） | **没有** |
| 禁用账户登录 | **没有** |
| 上传路径缺用户名、连接数上限 | 有（r13） |

## 2. F-097（P1）跨站写保护没有被证明过

`sameOrigin` 只有三行：

```go
parsed, err := url.Parse(origin)
if err != nil { return false }
return parsed.Host == host
```

这段代码是**防 CSRF 的唯一屏障**（配合 SameSite=Lax 的会话 cookie）。一旦写错——比如比较时带上/漏掉端口，
或者哪天改成"没有 Origin 就拒绝"——浏览器侧的攻击面就变了，而没有任何用例会红。

`TestCrossOriginWriteGuard` 四个断言：

| 场景 | 期望 |
|---|---|
| `Origin: http://evil.example` + POST | 403，文案 `cross-origin write rejected` |
| `Origin` 等于本站 + POST | 放行（由处理器返回 401，说明确实没被拦） |
| 无 `Origin` + POST | 放行（非浏览器客户端） |
| `Origin` 为异源 + GET | 200（只拦写） |

## 3. F-098（P2）禁用账户：顺序比判断更重要

`handleLogin` 里 `user.Disabled` 的检查在**口令校验之后**：

```
用户不存在   -> 401（并做等时哈希）
口令错误     -> 401
口令正确但禁用 -> 403 account is disabled
```

如果哪天有人把禁用判断挪到口令之前，就会多出一个"不用口令即可判定账户状态"的枚举面。
`TestDisabledAccountCannotLogin` 把这条顺序钉住：禁用账户 + 错误口令必须是 401 且响应里不含 `disabled`。
