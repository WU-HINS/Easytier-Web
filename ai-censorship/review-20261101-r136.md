# 第 136 轮评审（2026-11-01）— 转发头与第二条隧道

继续收 OPEN 单，这轮两条都在"信任边界"上。

## 1. F-216（P2）设备端口无条件相信 X-Forwarded-For

HTTP 侧早就有 `server.trust_proxy` 开关，README 也写明"关闭时任何转发头都不被采信"；
但设备拨入用的 WS 监听器（`internal/wire/ws.go`）**从不看这个开关**，
直接把 XFF 的第一段当成 `RemoteAddr()`。这个值会落库到 `devices.client_url`、出现在设备列表里。

修法：`ListenWS(addr, trustProxy func() bool)`，只有开关打开时才采信；
main 传一个读设置的闭包，改设置即时生效（不必重启）。

测试用两个子例（trusted / untrusted）真实拨一条 WS：

| 开关 | 期望 |
|---|---|
| 关 | RemoteAddr 是真实对端，不是 9.9.9.9 |
| 开 | RemoteAddr 取转发头 |

探针把判断改成恒真：`untrusted peer chose its own address: remote = "9.9.9.9"`。

## 2. F-218（P2）第二条隧道顶掉注册，旧的却还活着

同一设备开两条隧道时，`register` 直接覆盖注册表项，旧会话既不关闭也不报错；
于是管理员"阻止设备"时只关掉了注册表里的那一条，旧隧道继续心跳、继续刷新 `last_seen`，
而且 `bound` 之后不再复查封禁——"阻止立即生效"这条不变量被默默破坏。

修法：`register` 发现同 key 旧会话时先替换、再在锁外关掉旧 mux。
因为注册表只保留一个会话，"阻止"必然关到所有存活隧道，复查封禁也就不再必要。

测试用假隧道计数 Close：探针去掉关闭动作后 `the replaced tunnel was closed 0 time(s), want 1`。

## 3. 两条的共同点

都是"两套代码对同一个开关有两种态度"：HTTP 侧读开关，设备侧不读；
HTTP 侧只保留一个会话，设备侧却能并存两个。
修复方式也一样——**把判断收敛到一处，让另一处没有机会自作主张**。
