## 1. R-C 极端碰撞：F-018 闭环

**问题**：两次并发 `PUT /admin/settings` 为"最后写入者获胜"，A 改配额、B 改 OIDC 时，
B 的请求会把 A 看不见的字段覆盖（因为校验用的是 B 读到的旧状态）。

**实现**：

- 数据层新增 `settings.revision`（整数，随每次写入自增）与
  `PutSettings(ctx, values, expected *int)`，在**同一事务**内完成
  "读版本 → 比对 → 条件更新版本（CAS）→ 写业务键 → 提交"。
- 版本冲突时返回 `ErrSettingsConflict{Current}`，接口层映射为
  **409 `settings_conflict` + 当前版本号**。
- 整批写入仍是原子：任一键失败整体回滚（r4 的 F-017 修复保持有效）。
- 未带 `expected_revision` 的调用仍可用（兼容脚本/初始化），但同样自增版本，
  保证后续 CAS 调用者不会被"隐形的写入"坑到。

**回归** `TestSettingsRevisionConflict`：

```
初始 revision=0
A: PUT(quota=3, expected=0)   → 200, revision=1
B: PUT(quota=99, expected=0)  → 409 settings_conflict, revision=1
读回 quota                      → 3（B 的写入没有落地）
B 重读后重试                     → 200, revision=2
无版本号写入                     → 200, revision=3
```

前端同步：保存时携带 `expected_revision`，收到 409 后自动刷新并提示
"配置已被其他会话修改，已刷新为最新值，请确认后重试"。
