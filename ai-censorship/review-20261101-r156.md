# 第 156 轮评审（2026-11-01）— 最后一条 MONITOR：去上游找答案

F-066 挂了很久，理由一直是"需要上游语义输入"。这一轮发现：**输入就在仓库旁边**——
工作区里还留着上游源码的克隆，不必猜。

## 1. 上游到底怎么定义 instance_id

| 证据 | 内容 |
|---|---|
| easytier-proto/proto/core_config.proto:16 | NodeConfig.instance_id 是 common.UUID |
| easytier-proto/proto/api_manage.proto:23 | NetworkConfig.instance_id 是同一身份的字符串形式 |
| easytier/src/instance/factory.rs:353 | 用 instance.instance_id() 做 RPC 寻址（delete_network_instances） |

也就是说：上游的 instance_id 是**一条运行中实例**的标识，由实例自己生成，每次启动重新生成。

## 2. 我们怎么做的

central.InstanceID(networkID, deviceID)：sha256 派生 + 置 RFC 4122 版本位，
所以**同一设备接入同一网络，重启后 id 不变**。

| 维度 | 上游 | 本实现 |
|---|---|---|
| 生成时机 | 每次实例创建 | 确定性派生 |
| 重启后 | 变化 | 不变 |
| 唯一性范围 | 单个运行实例 | 单个网络成员 |

## 3. 判定：ACCEPTED，而不是 MONITOR

协议只依赖"一条实例一个标识"这一个性质——两边都满足。
差别在稳定性，而控制面**需要**稳定标识才能判断"这台设备是不是已经跑着这个网络"，
否则每次重启都会认为需要重新下发。所以这里是有意选择，不是遗漏。

写进 docs/PROTOCOL.md，附上游文件行号。若将来要与 2.7.0 的实例列表逐条对齐，
需要上游先引入稳定 id 的等价物——**这是上游的改动，不是我们的欠账**。

所以它最容易变成停车场。这一轮把它清空，靠的不是更强的意志，而是**把"需要外部输入"
