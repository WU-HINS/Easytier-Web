# 第 49 轮评审（2026-11-01）— JWT 校验的负向面

前两轮补的是"守卫有没有用例"。本轮换到**密码学边界**：id_token 的校验到底挡住了什么。

## 1. 已有的（写下来当基线）

`Provider.Exchange` 的校验顺序是：解析 header → 算法白名单 → 取 JWKS 公钥 → 验签 →
解析 payload → iss / aud / exp-iat / nonce。已有用例覆盖了：坏签名、错 audience、过期、
错 nonce、错 PKCE verifier。

## 2. F-102（P1）算法混淆：实现安全，但没有证据

`switch header.Alg` 只认 `RS256/384/512`，其余一律报错——这是对的，能挡住两类经典攻击：

- **alg=none**：伪造无签名 token；
- **HS256 混淆**：把公钥当 HMAC 密钥签名（因为公钥是公开的）。

但这两条**一行测试都没有**。哪天有人为了"兼容某个 IdP"顺手加上 `case "HS256"`，没人会察觉。

补齐：给假 IdP 加三个旋钮（`SetAlg` / `SetIssuer` / `SetKid`），
`TestExchangeRejectsAlgorithmConfusion` 逐个断言 `none`、`HS256`、`ES256`、`RS1` 都被拒；
`TestExchangeRejectsWrongIssuer` 与 `TestExchangeRejectsUnknownKeyID` 覆盖另外两个身份混淆面。

## 3. F-103（P2）state bag 的"缺 exp 视为无效"

`DecodeState` 里：

```go
if bag.Expires == 0 || time.Now().After(time.Unix(bag.Expires, 0)) {
    return StateBag{}, ErrInvalidState
}
```

**第一个条件最容易被写反**：如果只看 `After`，那么一个没有 `exp` 字段的包（`Expires == 0`
→ 1970 年 → 已过期）其实还是会被判过期……但如果有人把条件写成"有 exp 才比较"，它就永不过期。

`TestStateBagExpires` 三个断言：过期包被拒、无 exp 包被拒、异密钥签名的包被拒。
