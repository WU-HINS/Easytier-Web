# 第 14 轮评审（2026-11-01）— 机器驱动：协议层 fuzz

r13 的结论是"仍是人工构造的定向样本"。本轮把机器接上：引入 Go 原生 fuzz，
让引擎去找我没写出来的畸形输入。

## 1. 两个 fuzz target

| Target | 输入 | 不变量 | 结果 |
|---|---|---|---|
| `FuzzDecodePacket` | 任意字节 → 隧道包解码 | 不 panic；能解出来的必须能原样再编码（payload 不变、长度 = 头 + 载荷） | **42.5 万次执行，0 崩溃** |
| `FuzzFeedPacket` | 任意字节 → protobuf → 分片重组 | 不 panic；`MergerCount() <= 64`；在途字节 `<= 16 MB` | **11.2 万次执行，上限始终成立** |

第二个 target 是 r12 F-030 的机器化回归：人工用例只证明"我想到的那种攻击被挡住"，
fuzz 证明"任意 `total_pieces / piece_idx / transaction_id` 组合下预算都不破"。

## 2. 顺带补的最坏情况计时

`TestFeedWorstCaseTiming`（常驻用例）：

```
max pieces, tiny body      2.6 µs
max pieces, 8 KB body     12.5 µs
single piece 1 MB          2.7 ms
huge idx                  10.7 µs
```

结论：没有"一个包就能让重组卡住"的慢路径。1 MB 单片的 2.7 ms 是拷贝成本，不是算法问题。

## 3. 入口与门禁的关系

- **种子语料**随 `go test ./...` 默认执行（每秒级），所以每轮门禁都会跑；
- **扩展搜索**是可选步骤：`./scripts/fuzz.sh 60`，不进默认门禁（否则每轮多几分钟，团队会开始跳过）。

这条写进了 `docs/REVIEW-TEAM.md`：门禁要快，深度检查要显式触发。

## 4. 诚实记录：fuzz 没覆盖什么（F-036，MONITOR）

当前 target 每次都给**全新 Mux 喂一个包**。真实攻击面里有大量**跨包时序**：

- 交错多个 `transaction_id` 的分片；
- 先发 0 片、再补 1 片（fuzz 的随机输入几乎不会凑齐）；
- 超时后被清理的残片，再被旧 tid 的包"复活"；
- 同一 tid 被两个不同 descriptor 复用。

这些目前只有定向用例（`TestPartialPacketsAreBounded`、`TestLargeRequestIsSplitAndReassembled`）覆盖主路径，
登记为 F-036 观察项。要做需要**有状态 fuzz harness**（同一 Mux 连续 feed 序列 + 操作序列模型），
工作量比单包 fuzz 大一个量级，不适合在本轮夹带。
