# 第 127 轮评审（2026-11-01）— 同族的第二处，和一次不合格的探针

r126 修的是"HTTP 端口被占"，这轮按同一线索找同类：**还有哪些监听器失败会被吞掉**。

## 1. F-199（P1）额外 TCP 监听失败只打印一行

复现：后台开启"额外 TCP 监听"（端口 25222）→ 用另一个进程占住 25222 → 重启守护进程：

    console listening on http://127.0.0.1:25111
    extra tcp listener: wire: listen tcp 0.0.0.0:25222: ... address already in use
    （进程继续运行，直到被 timeout 杀掉）

设置页显示"额外 TCP 已开启"，实际没有任何监听。设备连不上，面板毫无提示。
这比 r126 更隐蔽：r126 至少整站不可用，这个只是"部分功能静默缺失"。

## 2. 修法

1. 额外监听绑定失败 → `return fmt.Errorf(...)`，退出码 1；
2. **"console listening" 移到所有监听器绑定之后**——一个在启动即将失败时打印的 listening 行，比没有更糟。

## 3. 门禁第 21 项扩展成两个场景

| 场景 | 断言 |
|---|---|
| 控制台端口被占 | 非零退出 / 无 listening / 有 bind 报错 |
| 额外监听端口被占 | 非零退出 / 无 listening / 有 extra tcp listener 报错 |

第二个场景要走 API 开启设置（setup → login → PUT settings），所以整项耗时约 10 秒。

## 4. 一次不合格的探针（值得记）

第一次探针是把 `return fmt.Errorf` 换回 `log.Printf`。结果检查**通过了**——
因为那样改之后 `extra` 变成了 nil，随后的 `extra.Close()` 直接 panic，进程以非零码退出，
恰好满足了"非零退出"这条断言。**探针失败的原因和被测行为无关。**

重做的探针改成"监听器忽略配置端口、改绑随机端口"：进程正常启动、正常服务，
于是两条断言同时命中：

    the daemon started without the extra listener it was told to open
    it still claimed to listen while the extra port was dead

这个教训和 r118 的"编译不过的探针"是同一族：**先确认探针失败在正确的地方**。

## 5. 台账

199 项：189 FIXED / 7 ACCEPTED / 3 MONITOR / 0 OPEN。

## 6. 判断

"配置了却没生效"这一类，连续两轮各抓到一个，而且都在启动路径上。
它们的共同点值得写进规范：**只要有一处"配置即承诺"，启动就必须要么兑现、要么失败**。
