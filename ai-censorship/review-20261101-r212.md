# 第 212 轮评审（2026-11-01）— 用公开节点做对照实验，问题收窄到"推送的 peer_urls"

用户给了公开节点 https://easytier.hinswu.top/@node/hins。抓下来是一组端点：

    wss://easytier.hinswu.top:443/@p2p/ixe312/
    wss://easytier.hinswu.top:443/@p2p/xc/
    tcp://v4v6.usvps.server.ddns.hinswu.top:21010
    udp://v4v6.usvps.server.ddns.hinswu.top:21010

## 1. 对照组：CLI 直连（成功）

    easytier-core --network-name X --network-secret Y --no-tun true -p tcp://…:21010

结果：peer 表出现 PublicServer_ser480657244709（289ms，tcp6），日志 new peer added。
**说明沙箱出得去、节点可用、无 tun 也没问题。**

## 2. 实验组：控制台下发的同一地址（失败）

网络创建时带 peer_urls，两台受管实例的 peer 表只有自己，客户端日志里连 connecting to peer 都没有。
也就是说：**配置里即使写了 peers，也比不上命令行 -p 的效果**，问题收窄到"推送的 peer_urls 没被采用"。

## 3. 下一步（很具体）

1. 把推送的 NetworkConfig 打印出来（在 reconcile 里加一条 debug 日志），确认 PeerUrls 字段确实非空；
2. 若字段为空 → 编译器或成员覆盖把它丢了；若非空 → 是客户端在 config-server 模式下忽略 peers，
   那就需要在实例创建时把 peers 带上（重启实例或改用 CLI 传参）。

## 4. 判断

这一轮没有把网络打通，但把"是环境的错"这个可能性彻底排除了——这是继续往下查的前提。
