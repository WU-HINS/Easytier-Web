# 第 130 轮评审（2026-11-01）— 被跳过的证据也是"通过"

这轮做一次**证据链自检**：账本与验收清单把 130+ 个用例当作结论的依据，
那么这些用例今天真的跑起来了吗？

## 1. 一次性把它们全跑一遍

从账本、验收清单、root.md、评审记录里收集全部被引用的用例名（去掉评审里贴的命令片段），
拼成一个 `-run` 正则，一次跑完：

    138 个被引用用例 → 134 个真实存在并运行 → 全部 PASS，0 FAIL

（另外 4 个是评审正文里的名字前缀，不是真实用例。）

## 2. F-203（P2）跳过的用例在 go test 里也算通过

第一次用**不带数据库变量**的环境跑同一套：

    citations: 3 cited test(s) skipped; the evidence is missing, not green

被跳过的正是三个 PG 专属用例（备份命令、全新库引导、缺表重建）。

问题在于：`t.Skip` 的用例在 `go test` 输出里是 `PASS`。
所以"门禁全绿"完全可能意味着"三条证据根本没跑"。

## 3. 固化成脚本

`scripts/check-citations.sh`：

| 断言 | 目的 |
|---|---|
| 收集到的名字不少于 100 | 防止文档被清空后空转 |
| 0 FAIL | 被引用的用例必须真的通过 |
| **0 SKIP** | 跳过不算通过 |
| 运行数不少于 100 | 防止 -run 正则失效 |

设好三个数据库变量后重跑：

    citations: 173 cited test(s) ran, none skipped, none failed

（173 > 134 是因为开启 PG 后同一批用例里包含子测试与 PG 分支。）

## 4. 记入深检台账

`docs/DEEP-CHECKS.md` 增加一行，并写明：**必须先设好 `EASYTIER_TEST_PG_DSN` 等三个变量**，
否则脚本会失败——这正是它该有的行为。

## 5. 台账

203 项：193 FIXED / 7 ACCEPTED / 3 MONITOR / 0 OPEN。

## 6. 判断

这一轮没有改动任何产品代码，但它回答了目标里最难的一句：**"证据是否成立"**。
现在这句话有一个可执行的答案：173 个用例、0 跳过、0 失败。
