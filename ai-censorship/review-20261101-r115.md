# 第 115 轮评审（2026-11-01）— 深检没有记录

这轮做两件事：跑一次全包数据竞争检测；把"深检"这件事本身变成有记录的动作。

## 1. 全包数据竞争检测

    go test -race -count=1 ./internal/...

结果：**0 处 DATA RACE，10 个包全部 ok**，退出码 0。
其中 httpapi 在 -race 下跑了 126 秒。

上一次跑这个深检是 r77，距今 38 轮——期间改过配额事务、租户守卫、路由外壳、缓存头、
还有 8 个前端组件的文案迁移。**结论：这些改动没有引入数据竞争。**

## 2. F-182（P2）深检只活在记忆里

root.md 与 REVIEW-TEAM 都写着"设 `EASYTIER_RACE=1` 可加数据竞争检测"，
但**没有任何地方记录它到底什么时候跑过、结果如何**。
于是"我们做过深检"变成一句无法核对的声明——和 r95 那条永远为真的断言是同一种病。

新增 `docs/DEEP-CHECKS.md`：每次深检记录 轮次 / 日期 / 项目 / 命令 / 结果，
并列出"还没做的深检"（PostgreSQL 浸泡、协议模糊长跑、更长随机序列）。

## 3. 让记录也被检查

check-docs 新增第 9 条规则：`DEEP-CHECKS.md` 里引用的每个轮次都必须有对应的评审记录，
且不允许一张空表。这条规则当场就抓住了我自己——写文件时 r115 的记录还没建：

    DEEP-CHECKS cites round r115 with no review record

写完这份评审后转绿。

## 4. 本轮验证

    go test -race -count=1 ./internal/...   0 DATA RACE / 10 包 ok
    node scripts/check-docs.mjs             PASS（含新增第 9 条规则）

## 5. 台账

182 项：172 FIXED / 7 ACCEPTED / 3 MONITOR / 0 OPEN。

## 6. 判断

深检的价值在于"偶尔跳出默认速度去看一眼"。但如果没人记录，它就会退化成一种心理安慰：**跑没跑过、结果如何，全靠记忆**。
现在这条记忆有了落款和校验。
