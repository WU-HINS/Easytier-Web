# 第 241 轮评审（2026-11-01）— 日志级别：一次命名错误伪装成"做不到"

上一轮我把日志级别记成 OPEN，理由是"没有 api.logger 的生成包"。这一轮先给 Caller 加了原始字节通道，
然后用 protowire 按 api_logger.proto 的字段号构造请求——结果设备回：

    InvalidService: "api.logger.LoggerRpcService"

换了个服务名再试：

    ProtoName="LoggerRpc", ServiceName="LoggerRpc"  →  {"level":"disabled","value":0}

**成了。** 也就是说：

- 生成包确实缺，但那不是阻碍——CallRaw 绕过了它；
- 真正的阻碍是我把 methodindex 里的**全名**当成了注册表键，而设备注册的是**短名**。

## 1. 实现

| 层 | 改动 |
|---|---|
| rpc | Mux.CallRaw：发送已编码字节，不再要求 proto.Message |
| session | Manager.CallRaw：同一套协议名回退逻辑 |
| legacyview | GetLoggerLevel / SetLoggerLevel：protowire 构 field 1 varint |
| httpapi | GET/PUT /machines/{id}/logger-level（未知级别返回 400，不是静默默认） |
| 前端 | 实例详情里的日志级别选择器，注明"作用于整台设备" |

## 2. 真机实测

    读：disabled (0)
    设：info → {"level":"info","value":3}
    读：info (3)          ← 设备侧真的改了
    设：verbose → 400 unknown log level
    复位：disabled (0)

单测固定了字节形状：debug 对应 payload = 08 04（field 1, varint, 4）。

## 3. 教训

上一轮我说"这一步不该我一个人拍板"，其实**我可以自己验证**——只差一个 CallRaw 和一次重试。
把一个可验证的问题报成需要决策的问题，是另一种偷懒。
