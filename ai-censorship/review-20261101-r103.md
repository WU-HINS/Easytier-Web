# 第 103 轮评审（2026-11-01）— 租户隔离靠"每个人都记得"

r102 把管理面守住了（每条 /admin 路由必须有外壳）。这轮看另一半：
**用户面的数据查询有没有一直带着租户条件**。

## 1. 先扫一遍现状

对 bal 里五个租户表（networks / network_members / devices / network_credentials / running_configs）逐条看语句，
**没有发现漏了 user_id 的查询**。也就是说当前是干净的——但它靠的是"每个写查询的人记得"。

## 2. F-171（P2）把"记得"变成检查

`TestTenantTablesAreAlwaysQueriedWithAUser`：扫描 `internal/db/bal`，
凡以 `query.From` / `query.Into` / `query.Table` 开头、以 `.Build(` 结尾的语句，
只要目标是上述五张表之一，就必须出现 `user_id`；并要求扫描到的语句数不少于 12（防空转）。

## 3. F-172（P2）第一版守卫是假的

第一版用"语句附近 14 行内出现 user_id"判定。自测把一条过滤条件删掉——**仍然通过**：
窗口里还留着相邻查询的 user_id。

    （探针）删掉 Where("user_id", "=", userID) → 测试 PASS

这正是这个会话里反复出现的形状：**检查器看起来在检查，实际在看别的地方**。

改成按语句跨度判定后，同一个探针稳定失败，并指出具体语句：

    internal/db/bal/networks.go queries networks without a user_id predicate:
      query.From("networks").Columns(splitColumns(networkColumns)...).

顺带发现：跨度扫描只能覆盖用构建器拼的 15 条语句，手写 SQL 的（如 `CountMembersByUser`）不在其中——
这一条已写进评审记录，作为后续可加强项。
