# 第 73 轮评审（2026-11-01）— 对账和会话也只在一种库上跑过

r72 解决了 REST 套件的方言问题。但真正的核心路径——**对账收敛、配额裁剪、重连补发、空闲超时**——
都在 `internal/e2e` 里，而它们全部写死了 SQLite。

## 1. F-133（P1）16 处调用点，9 个文件

e2e 的每个测试都自己开库：

    store, _, err := db.OpenWith(ctx, db.Config{
        Driver: dal.SQLite, DSN: filepath.Join(t.TempDir(), "et.db"), AutoAlign: true, Backup: false,
    })

本轮统一成 `newTestStore(t, ctx)`：

| 环境 | 行为 |
|---|---|
| 未设置 | 临时 SQLite 文件（与之前完全一致） |
| `EASYTIER_E2E_PG=<dsn>` | 每个用例一个私有 schema，通过 options 设 search_path，结束即删 |

结果：**双方言全绿**（18.5s / 20.9s）。门禁新增第 17 项 `postgres e2e`。

## 2. 一个防止"假通过"的守卫

如果环境变量被忽略，所有场景仍会通过——只是从没在第二种方言上跑。所以加了 `TestE2EStoreDialect`：
设置变量时断言 store 的方言必须是 postgres。r72 的 REST 套件用的是同一条思路。

**"我配置了双数据库"和"双数据库真的都被跑过"，中间差一个断言。**

## 3. 机械重构的风险与自证

这次改动是"脚本批量替换 16 处 + 删 27 个多余 import"，属于容易出错的操作。事实上有两个保护：

1. `go vet` 立刻报出 `path/filepath imported and not used`，逼我把 import 清干净；
2. 改完后 SQLite 与 PostgreSQL 都全绿——如果替换漏了某处（比如留着旧的开库代码），两条都会崩。

## 6. 判断

到本轮为止，"支持两种数据库"在三个层次都有双方言证据：

| 层次 | 用例 |
|---|---|
| 数据层 | db 包（表结构、升级、快照、并发） |
| 接口层 | 70+ REST 用例（r72） |
| 场景层 | 10 个端到端场景（本轮） |

这是"声明支持"和"实际支持"之间的距离。
