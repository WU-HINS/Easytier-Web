# 第 70 轮评审（2026-11-01）— 让"没跑"变成红色

r69 的教训是"断言可能根本没执行"。这一轮把它变成机制，并顺手挖出两个更大的问题。

## 1. F-126（P2）冒烟现在会证明自己跑过

`step()` 把每个步骤名写进 `steps.txt`，脚本末尾逐个校验 11 个关键断言是否真的执行过：

```
== assertion coverage ==
assertions ran                 26 steps
```

自测：把 `override applied on device` 注释掉 →

```
FAIL: step never ran: override applied on device
```

**"没跑了"和"跑过了"从此不再看起来一样。**

## 2. F-127（P2）完整冒烟从来没在 PostgreSQL 上跑过

顺着这条线检查 `SMOKE_PG_RESET` 分支，发现那条 `psql` 命令是坏的：

```sh
psql -q "$DSN" -c "DROP SCHEMA ..." > /dev/null 2>psql "$DSN" -c "DROP SCHEMA ..." > /dev/null1
```

`2>psql ... 1` —— 明显是历史某次编辑事故，而且因为没人设过 `SMOKE_PG_RESET=1`，它一直没被执行。

修好之后在 PostgreSQL 上把整个流程跑通（空库建表 → setup → 注册 → 设备 → 下发 → 覆盖 → 关停 → 重启 → 独立 ws），
并把它加成门禁第 15 项 `postgres deploy`。

这条的价值：此前 PostgreSQL 只有**单元/接口级**用例，**没有一次端到端的部署走查**。

## 3. F-128（P2）同一规则的两份实现互相打架

加完 `postgres deploy` 后 `check-docs` 报错，但我刚写的表格行明明在。原因是：

> `check-docs.mjs` 里有**两份**门禁表校验。r59 我加了一份（解析 `run`/SKIP + 第 3 节表格），
> 而更早的那份还在（只认"表格行里带反引号"的），两份口径不同 → 一条说"章程没写"，另一条说"脚本没跑"。

删掉旧实现，只留一份。**重复的检查比没有检查更危险**：它们会给出互相矛盾的结论，让人开始怀疑检查本身。
