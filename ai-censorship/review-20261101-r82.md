# 第 82 轮评审（2026-11-01）— 限流器：一个测试都没有

前六轮都在扫"先读后写"。这轮换了个问题：**哪个安全控制还没有测试？**

第一个撞上的就是登录限流器。它是在线爆破的唯一屏障，而 `internal/httpapi/ratelimit.go` 里一条用例都没有。

## 1. F-145（P2）限流器只有意图，没有规格

代码写着：每个 (地址, 账号) 3 次失败后拒绝、每个地址 30 次、成功清零、窗口 5 分钟。
这些数字此前**没有任何断言**——改错了不会有人发现。

补上的用例覆盖五件事：

| 行为 | 断言 |
|---|---|
| 阈值 | 前 3 次允许，第 4 次拒绝且给出 retry-after |
| 分桶（账号） | 同地址换一个账号仍允许 |
| 分桶（地址） | 换一个地址不受影响——**一个客户端不能把别人的账号锁死** |
| 成功 | `reset` 清空窗口 |
| 过期 | 窗口过后自动恢复 |

第三条是这类控制最容易被写坏的地方（按账号全局计数 = 拒绝服务放大器），现在有断言钉住。

## 2. F-144（P2）sweep 是死代码

限流器里有个 `sweep()` 方法负责删过期条目——**没有任何地方调用它**。

后果不是"偶尔多占几 KB"：条目只在同一 key 复用时被覆盖，所以**每个不同的用户名都会永久留下一行**。
攻击者用随机用户名打几次，映射就只增不减。

修法：`allow()` 在超过一个窗口时先清理。为了避免两份删除逻辑，把循环提成 `sweepLocked`，
原来的 `sweep()` 也改成调用它。

负向自测：把清理关掉，`TestLoginLimiterDropsExpiredWindows` 立刻报 `expired windows were kept: 402 entries left`。
