# 第 93 轮评审（2026-11-01）— 让"门禁全绿"本身可被质疑

r92 抓到一条从未生效的守卫。那轮之后有个问题没解决：**下一轮新加的检查，凭什么不会同样空转？**
答案是每轮手工做负向自测——而"手工"意味着会漏、会忘、会做错（r91 我就写错过一次）。

## 1. 写一个审计脚本，逐个把检查打红

`scripts/audit-gates.sh`：把仓库复制到临时目录，对 9 条静态检查**逐个破坏被测物**，
要求每一条都变红，然后再复原、再确认回绿。

| 破坏什么 | 应当变红的检查 |
|---|---|
| `--phi: 1.618034` → `1.5` | design tokens |
| 把 `--muted-foreground` 亮度提到 97% | design contrast |
| 客户端的 `/networks` → `/networksX` | api contract |
| uuid 取 6 字节而非 8 | wire format |
| 账本里加一个不存在的测试名 | docs consistency |
| README 里加一个不存在的参数 | readme commands |
| 往组件里塞 `dangerouslySetInnerHTML` | ui states |
| 让 `isSecureOrigin` 恒真 | client origin |
| 去掉 `credentials: same-origin` | client request |

## 2. 第一次运行就抓到一个（F-158）

    VACUOUS  design tokens (checker stayed green after the breakage)

改 `--phi` 居然不影响 "design tokens" 这一项——因为它只在**组件**里找硬编码字面量，**从不看 token 文件本身**。
而设计规范宣称的正是"所有尺寸 = 8·φ^((n-3)/2)"。

补上：φ 必须等于 1.618034，`--u-1..--u-12` 必须落在公式 ±1px 内（实测 12 级全部吻合）。现在改 φ 或改任一级阶梯都会红。

## 3. 一次自己造成的事故（必须记下）

第一版审计脚本在**原仓库**上改文件，用 shell 数组存备份。数组还原那步写错了，
结果 **9 个文件全部留在"被破坏"状态**：README 里多了个假参数、账本里多了一行 F-999、
组件里多了个 `dangerouslySetInnerHTML`、`origin.ts` 的 `isSecureOrigin` 恒真……

发现后逐个复原并核对（六类残留全部归零），然后把脚本改成**只在副本上操作**：

    tar --exclude=node_modules --exclude=dist --exclude=.toolchain | tar -x   # 到 mktemp -d

这件事本身值得记：**一个用来验证别人不撒谎的脚本，先得自己不撒谎。**
如果它跑在门禁里而中间被打断，会留下一棵"看起来正常、实际被改过"的树。

## 4. 现在它进了门禁（第 20 项）

耗时 2.6 秒，不碰工作树。它把"这些检查能不能变红"从**每轮的手工仪式**变成了**机器事实**。
