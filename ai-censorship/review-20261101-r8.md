# 第 8 轮评审（2026-11-01）

本轮把"完整从 0 部署"这条维度**推到另一个数据库方言**上，结果抓到一个 P0。

## 1. R-B 部署：F-023（P0）全新 PostgreSQL 库启动失败

**现象**：空库 + `EASYTIER_DB_DRIVER=postgres` 启动：

```
easytier-webd: schema: apply create table blocked_devices:
  ERROR: relation "users" does not exist (SQLSTATE 42P01)
```

**根因**：`dsm.Plan` 生成变更后按"阶段 → 表名"排序，把 `Export()` 已经排好的
外键拓扑序（users 先于 blocked_devices）**重新打乱**了。SQLite 在 CREATE TABLE 时不校验
父表是否存在，所以这个问题一直被掩盖；PostgreSQL 立刻拒绝。

**为什么之前没发现**：所有 PG 用例都跑在**已有 schema** 的库上（`easytier_test`），
"全新库"这条路从未被走过。这正是"完整从 0 部署"该覆盖而没覆盖的角落。

**修复**：`Change` 增加 `Order`（声明序号），阶段内按它排序，
保留 `Export` 的拓扑顺序。

**回归** `TestFreshPostgresBootstrap`：临时创建 `et_fresh_<n>` 数据库 →
对齐 → 断言建表数 ≥ 8 → 再对齐一次断言零 DDL → 清理。修复前该用例等价场景实测报 42P01。

## 2. R-B 部署：F-024（P2）冒烟脚本自身的续行 bug

给冒烟脚本加"可选 PostgreSQL"时，环境变量前缀与二进制之间的 `\` 续行符在编辑中丢失：

```
EASYTIER_DB_DRIVER="$DRIVER" EASYTIER_DB_DSN="$DSN"
  "$BIN" --http ... &
```

结果 PG 路径下守护进程**没有拿到任何数据库配置**，直接退出，脚本只表现为"全部 000 超时"。
这条很能说明问题：**部署脚本本身也要被测**，否则它会用"看起来在跑"掩盖失败。

修复后续行恢复，PG 冒烟实跑：

```
database                       postgres
setup status (before)          {"initialized":false}
gate before setup              409
setup admin                    {"role":"admin","username":"root-owner"}
register user                  {"role":"user","username":"alice"}
csp header                     Content-Security-Policy: default-src 'self'; script-src 'self'; ...
ws route (no upgrade)          400
boot js served                 200
```
