# 第 75 轮评审（2026-11-01）— 密码泄露了，用户自己改不了

v3 需求写得很清楚：**管理员对用户只读**（不能改密码/凭证/绑定）。这条一直守得很好——好到
没有任何人能改密码：

| 角色 | 能不能改这个用户的密码 |
|---|---|
| 管理员 | 不能（设计如此） |
| 用户本人 | **也不能（根本没有接口）** |

## 1. F-135（P2）凭证只能创建，不能轮换

注册时设的密码就是永久密码。泄露之后的唯一出路是请管理员删号重建——而删号会连带删掉设备、网络和成员关系。

这不是"缺个按钮"，是**凭证生命周期缺了一半**。

## 2. 实现要点

| 检查 | 为什么 |
|---|---|
| 校验当前密码 | 防止会话被劫持后直接改密 |
| 复用登录限流 | 否则这里成了爆破当前密码的新入口 |
| 新旧不得相同 | 便宜但有效的小约束 |
| 走密码策略 | 与注册/初始化同一套规则 |
| 成功后清空该用户**全部**会话，再给调用方重新签发 | 改密的语义就是"其它地方都下线" |
| 管理面不新增改密能力 | 只读约束不能被顺手打破 |

## 3. 用例覆盖的六件事

`TestPasswordRotation` 断言：

1. 当前密码错 → 401，且**其它会话不受影响**（失败不该误伤）；
2. 新密码太弱 → 400（策略生效）；
3. 改密成功 → 204；
4. 调用方自己仍在登录（不会被自己踢掉）；
5. 另一个浏览器的会话 → 401；
6. 旧密码登录 → 401，新密码 → 200；再确认 `POST /admin/users/{id}/password` 依旧 404（管理面没有这个能力）。

## 4. 过程中的两个坑

- 一开始把列名写成 `password_hash`，实际是 `password`——错误被处理器吞成了"cannot store the new password"，
  改成打印底层错误之前先对着 schema 核对了一遍；
- UI 侧用了 `Field`，但它只是 settings 页的**局部组件**，不是 ui 导出——tsc 立刻报错，改成 label 包裹。

## 7. 判断

"只读管理"是一个正确但容易被误读的约束：它说的是**管理员不能碰别人的凭证**，
而不是**凭证永远不能变**。这两件事只差一个自服务接口，却决定了泄露之后能否自救。
