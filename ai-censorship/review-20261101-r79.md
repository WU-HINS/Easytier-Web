# 第 79 轮评审（2026-11-01）— 同名首次 SSO 登录

r76/r78 的规律：**读一个数、据此决定要不要写，在 PG 上不安全**。继续扫，这次落在 OIDC 首次登录上。

## 1. F-141（P2）先查重名，再插入

provisionOIDCUser 原来是：

    for attempt := 2; attempt < 20; attempt++ {
        taken, _ := ExistsByUsername(candidate)
        if !taken { break }
        candidate = fmt.Sprintf("%s-%d", username, attempt)
    }
    UpsertOIDCUser(..., candidate, ...)

两个**不同身份**（比如两个都在 IdP 里叫 alice 的人）同时首次登录：
两边都查到 "alice" 被占、都改成 "alice-2"、都插入——输的一方拿到唯一约束错误。

实测（把重试关掉的负向自测）：

    SQLite: bal: upsert oidc user: constraint failed: UNIQUE constraint failed: users.username (2067)
    PG:     bal: upsert oidc user: ERROR: duplicate key value violates unique constraint "uq_users_username" (SQLSTATE 23505)

对用户来说是 500 加一段驱动原文——一次正常的双击登录就能撞上。

## 2. 修法：重试放到约束旁边

把"选名字"的循环从 handler 移到 store：

| 位置 | 原因 |
|---|---|
| 在 `UpsertOIDCUser` 内部 | 唯一约束就在这里，冲突可以就地换名重试 |
| 最多 20 次 | 与原来的上限一致，防止病态循环 |
| 判定依据 `users.username` / `uq_users_username` | 两个方言的报错文本都能命中，不会误吞其它约束 |

handler 里那段 `ExistsByUsername` 循环删掉（保留保留名校验）。**同一逻辑只留一份**，这也是 r70 的教训。

## 3. 验证

`TestOIDCUpsertPicksAFreeUsername`：先建一个 "alice"，再让 6 个身份并发首次登录、preferred 都是 "alice"。断言：

1. 六个都成功（没有 500）；
2. 没有一个拿到 "alice"；
3. 六个用户名互不相同；
4. 同一身份再登录一次，回到同一个账号（名字不漂移）。

方向自测：把重试短路后，SQLite 与 PostgreSQL **分别在各自的错误文本上失败**——证明这段重试是承重的。
