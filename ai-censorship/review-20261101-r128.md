# 第 128 轮评审（2026-11-01）— 顺序用例通过，不代表并发安全

前两轮在启动路径上收口，这轮回到 R-D（极端碰撞）。挑的是**已经有测试**的地方：设置的修订号 CAS。

## 1. F-200（P2）CAS 只有顺序用例

现有用例（r5 起）：写 A 用 rev 0 成功 → 写 B 用 rev 0 被拒 409。

问题：如果实现是"读 rev → 比较 → 写"，**这条用例照样通过**，因为没有任何并发。
它验证的是"我比较了"，不是"比较和写入之间没有空隙"。

## 2. 实现本身是原子的

读代码确认：修订号更新是**带条件的 UPDATE**（`WHERE key=? AND value=?` 并检查 affected），
所以两个事务同时读到 rev 0 时，第二个会阻塞在行锁上、拿到锁后条件不成立、影响行数为 0 → 冲突。

实现是对的——**但没有用例证明它是对的**。

## 3. 新用例：6 个写者同时持 rev 0

断言三件事：

| 断言 | 期望 |
|---|---|
| 200 的数量 | 恰好 1 |
| 409 的数量 | 恰好 5 |
| 最终 revision | 仍为 1（不是 6） |

SQLite 与 PostgreSQL 各跑一次（`EASYTIER_HTTPAPI_PG`）。

## 4. 探针

把条件 UPDATE 换成不比较旧值的版本：

    --- FAIL: TestConcurrentSettingsWritesKeepOneWinner
        0 writers won the same revision, want exactly 1
    --- FAIL: TestSettingsRevisionConflict

两条同时红——说明并发用例补上的正是顺序用例看不见的那一面。

## 6. 判断

这是本会话里重复最多的一条教训，第 N 次出现：**顺序用例证明不了并发安全**。
r76（单管理员）、r78（配额）、r80（注册）、r103（租户）、r118（注销）、r128（CAS）——
同一件事被反复验证，因为每次都是"有测试，但测的是别的东西"。

## 7. 新用例自己抓到一个 P1（F-201）

写完之后跑完整门禁：`postgres api` 红了。但门禁当时只打印最后 20 行日志，
里面全是健康的 INFO 行——**看不到是哪个用例失败**。

先把门禁的失败输出改成"额外打印 --- FAIL 与 _test.go:行号"（这本身也是修复），
再按门禁的顺序（先 `./internal/db/... ./internal/httpapi/...`，再 `EASYTIER_HTTPAPI_PG` 跑 httpapi）复现，
拿到真凶：

    writer 3 got 500 {"message":"bal: seed revision: ERROR: duplicate key value
    violates unique constraint "settings_pkey" (SQLSTATE 23505)"}

两个问题一起暴露：

| 问题 | 说明 |
|---|---|
| 播种不幂等 | 全新实例**第一次**保存时，修订号行不存在 → 普通 INSERT → 并发下唯一约束冲突 |
| 错误外泄 | 500 的响应体里带着表名与 SQLSTATE——r19 立过的规矩在这里被绕过了 |

为什么顺序用例和单独跑都碰不到？因为 setup 之后修订号行通常已经存在，
只有"全新实例 + 两个管理员同时第一次保存"才会走到播种分支。

修法：播种改成 `ON CONFLICT (key) DO NOTHING` 并在同事务内回读修订号；
处理器把 500 换成通用文案，真实错误只进日志。

修完后按同样的顺序复现一次：通过（119s，无失败）。
