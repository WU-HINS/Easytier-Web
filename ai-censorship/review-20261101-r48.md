# 第 48 轮评审（2026-11-01）— 会话生命周期

延续 r47 的守卫扫描，本轮看"会话过期"和"用户被删除"这两条**生命周期边界**。

## 1. F-100（P2）过期的真正防线是懒判断，不是清理任务

代码里有两处涉及过期：

```go
// GetSession：读的时候判断
if time.Now().After(session.Expiry) {
    _ = s.DeleteSession(ctx, sid)
    return SessionData{}, ErrNotFound
}

// PurgeExpiredSessions：每 5 秒清一次
DeleteFrom("sessions").Where("expiry", "<", now)
```

守护会话安全的是**第一处**：它保证"过期即失败"，与清理任务的节奏无关。
第二处只是清理垃圾——如果哪天有人觉得"有清理就够了"而删掉第一处，被盗 cookie 会一直有效到下一次 tick，
而在非守护进程的场景（测试、嵌入式）里根本没有 tick。

`TestExpiredSessionIsRejected` 直接写入一条过期会话再请求受保护接口：401，且该行在查询时就被删掉。

## 2. F-101（P2）删除用户之后，他的 cookie 会怎样？

这是一个真实运维动作：管理员删掉某人，但对方浏览器里的 cookie 还在。
期望是**立刻失效**，且**不能是 500**（500 会把内部状态暴露给已删除用户）。

`TestSessionOfDeletedUserIsRejected`：登录 → 管理员删除该用户 → 同一 cookie 请求 `/console-info` → **401**。
既不是 200（数据仍可读），也不是 500（内部错误泄露）。

## 4. 判断

这两条都属于"实现是对的、但没人证明过"的类型。会话是控制面里**唯一长期有效的凭证**，
它的失效条件（过期、用户被删、禁用）应当各有一条用例；现在三条都有了。

（禁用那条在 r47 补过——注意它只在**登录时**检查，已登录会话不受影响。这是有意为之：
禁用是"不许再登"，不是"立刻踢下线"。如果要后者，需要额外的会话失效机制，登记为后续可选增强。）
