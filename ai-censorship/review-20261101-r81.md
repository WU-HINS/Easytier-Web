# 第 81 轮评审（2026-11-01）— 把"人工逐个发现"变成规则

r76 到 r80 的四条问题（F-137、F-140、F-141、F-142）是**同一个形状**：先读一个数，再据此决定要不要写。
每一轮都是人工扫出来的。这轮把它变成机器规则。

## 1. 两条新守卫

| 守卫 | 规则 | 为什么 |
|---|---|---|
| `TestHandlersDoNotKnowDriverErrors` | `internal/httpapi` 不得出现 `sqlstate` / `duplicate key value` / `unique constraint failed` | 约束翻译属于数据层；handler 嗅探驱动文本正是 r80 里 500 的成因 |
| `TestGuardThenInsertIsReviewed` | 同一函数里既有 `Store.Exists/Count` 又有 `Store.Create/Add/Upsert`，必须在白名单里写明原因 | 这条形状出过四个 P1/P2 |

白名单当前只有两条，各带一句理由：

    handleRegister   唯一索引兜底 + CreateUser 映射成 409
    handleAddMember  AddMembersBounded 在事务内持租户行锁再计数

**白名单不是免死金牌，是"这条我读过并知道为什么安全"的记录。**

## 2. 顺手修掉最后一处驱动文本嗅探

handleCreateNetwork 里原本自己判断：

    if strings.Contains(lowered, "sqlstate 23505") || ... { 409 }

这既是重复实现（r79 已经把这些判定放进 bal），也违反了新规则。下沉成 `bal.ErrNetworkExists`，
判定用 `isNetworkNameViolation`（在通用唯一冲突之上再收窄到 `networks.` / `uq_networks_`，
免得将来别的约束被误认成网络重名）。handler 只认哨兵。

## 3. 负向自测

放一个临时探针文件，同时触发两条规则：

    probeGuardThenInsert  先 Exists 再 Create
    probeDriverText       比较 "SQLSTATE 23505"

两条守卫**都红**，各自点名了该文件与函数；删掉探针后恢复绿。
