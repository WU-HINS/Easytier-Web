# 第 105 轮评审（2026-11-01）— 认证数据没有缓存策略

这轮回到红蓝攻防（R-E）。安全头都齐了，但漏了一类：**缓存语义**。

## 1. F-174（P2）/api/* 既无 Cache-Control 也无 Pragma

现状：只有单页入口设了 `Cache-Control: no-cache`，所有认证后的 JSON 响应没有任何缓存指令。

风险不在于浏览器（现代浏览器对带 Cookie 的 GET 不会自作主张缓存），而在于**共享缓存**：
上游若按启发式规则存储了一个 200，它对"下一个带着别的 cookie 的请求"没有任何办法区分——
租户 A 的设备列表可能被端给租户 B。

## 2. 修法：按前缀给策略，而不是一刀切

    if strings.HasPrefix(r.URL.Path, "/api/") {
        header.Set("Cache-Control", "no-store")
        header.Set("Pragma", "no-cache")
    }

静态资源保持原样（带哈希的文件名本来就该缓存），单页入口继续 `no-cache`。

## 3. 用例同时盯两件事

`TestApiResponsesAreNeverCached`：

1. 认证后的 `/api/v1/machines` 必须含 `no-store` 与 `Pragma: no-cache`；
2. `/boot.js` **不得**被误加 `no-store`（防止我把它做成全局一刀切，
   顺带把静态资源缓存也废掉）。

第 2 条是这次刻意加的：**防过度修复**和防漏修一样重要。

## 4. 探针的两次折腾

| 尝试 | 结果 |
|---|---|
| 把判断条件改成 `if false` | 编译失败（`strings` 变成未使用导入），测试根本没跑 |
| 把值改成 `public, max-age=3600` | `API Cache-Control = "public, max-age=3600", want no-store` |

第一次那种"探针没生效"的情况在这个会话里出现过好几次了。判断标准很简单：
**探针后先看测试是真跑了还是编译失败**，再看输出。

## 7. 判断

安全头清单里最容易被忘的就是缓存：它不改变"谁能访问"，只改变"**访问结果能留多久、留在谁那里**"。
这类问题在本地永远复现不出来，只能靠策略默认为严。
