# 第 89 轮评审（2026-11-01）— 网络密钥会不会被顺手带出来

r88 守住了"OIDC client secret 不上电视"。这轮问同一个问题：**网络密钥呢？**

`networks.network_secret` 是派生设备凭据的原料。它落在浏览器里，就等于落在截图、代理日志、
以及任何能读到响应体的地方。而"不返回它"此前只是**没人顺手加过**，不是被断言过。

## 1. F-153（P2）四个响应，一处都没断言

| 端点 | 是否可能带出密钥 |
|---|---|
| `POST /networks`（创建） | 显式指定密钥时，回显是最容易发生的 |
| `GET /networks` | 列表里塞一个字段就够了 |
| `GET /networks/{id}` | 详情最容易"顺便带全" |
| `GET .../members` | 成员视图也可能带上网络材料 |

## 2. 用例怎么写才不是空转

`TestNetworkSecretNeverLeavesTheServer` 做了三件事：

1. **显式指定**一个密钥建网络（而不是让它随机生成）——否则断言"响应不含密钥"毫无意义，因为我们不知道密钥是什么；
2. 断言建网响应不回显，随后三个读接口逐一断言不含该字符串；
3. **同时断言数据库里存的确实是指定值**，排除"根本没存所以没泄露"这种假绿。

第 3 条是关键：没有它，"密钥没出现"可能只是因为**密钥压根没写进去**。

## 3. 负向自测

把 `network_secret` 加进两个响应后：

    /api/v1/networks leaked the network secret:
    {"networks":[{"display_name":"secret-net","member_count":0,"network_id":"ea94027b-...",
                  "network_name":"secret-net","network_secret":"known-secret-value-123",...}]}

失败信息直接把泄露体打出来——**这正是"顺手加一个字段"会长的样子**。

## 4. 顺带确认的一件事

用界面建网络时请求里没有 `network_secret` 字段，所以密钥是服务端生成的、**用户永远看不到**。
这不是缺陷：设备从对账拿到的是派生凭据，不需要原始密钥。但如果用户想用同一套网络名/密钥在别处手动起一个设备，
就得在创建时自己指定密钥（API 支持，界面暂未暴露）。这条已写进本轮记录，留作后续 UI 选项。

## 7. 判断

"敏感字段不会被返回"是一个**容易保持、也容易被无意打破**的属性：
加一个字段是顺手的事，而它需要有人专门写一条断言才守得住。
