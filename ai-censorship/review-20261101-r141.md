# 第 141 轮评审（2026-11-01）— 整行写回的病，治在一个函数上

R-D 在上一轮指出的 F-228 是这一轮唯一的目标：成员编辑的**整行读改写**。

## 1. 病在哪

    member := GetMemberByDevice(...)   // 读整行
    if payload.HostnameOverride != nil { member.HostnameOverride = ... }
    UpdateMember(member)               // 把 7 个列全部写回

两路并发 PATCH 各改一个字段时，后写者用**自己读到的旧行**覆盖前者，双方都收到 204。
被覆盖的列里还有 credential_id / acl_group_secret——这两个列上有 CHECK 约束，
一旦将来有别的写入者动它们，就会从"丢更新"升级成"约束 500"。

## 2. 修法：让"没说到的列"真的不被写

    type MemberPatch struct {
        HostnameOverride *string
        VirtualIPv4      *string
        OverrideConfig   *string
        ClearHostname    *bool   // 显式置空
        ClearIPv4        *bool
    }

SQL 只 SET 载荷提到的列，update_time 单独更新。两个调用点（成员编辑、override_config 编辑）都改为传 patch。

**三态是关键**：nil = 不动；用户想让某列为 NULL 必须用显式标志，不能靠空串传意。

## 3. 证据

新增 TestConcurrentMemberPatchesKeepBothFields：两路并发，一路改 hostname_override、一路改 virtual_ipv4，
断言最终两者都在。

探针（把 handler 改回"每一列都写给空串"）：

    virtual_ipv4 = 0xc000284150, the other patch undid it

## 4. 台账

230 项：218 FIXED / 7 ACCEPTED / 3 MONITOR / **2 OPEN**。

剩两条都属部署面：F-229（备份链路从未被演练）、F-230（DSN 带参数时 pragma 被静默丢弃）。

## 5. 判断

"先读再写整行"这种写法，靠加锁是治不好的——锁只保证这一行这次不被别人改，
挡不住"我读到的旧值覆盖了别人的新值"。解法是让写入粒度与业务粒度对齐：
**你只想改一个字段，就只发一个字段的 UPDATE**。
