# 第 58 轮评审（2026-11-01）— 守卫自己的漏洞

前三轮在扫"管理动作与效果之间的时延"。本轮转向**守卫本身**：那些用来防止规则被破坏的测试，自己有没有洞。

## 1. F-114（P2）分层守卫用硬编码列表

`internal/arch` 的第一条测试是这样开头的：

```go
businessDirs := []string{
    "internal/httpapi", "internal/session", "internal/central",
    "internal/rpc", "internal/wire", "internal/oidc", "cmd",
}
```

也就是说：**新增一个业务包，只要没人记得把它加进这张表，它就可以直接 import `internal/db/dal`**。
守卫依赖"有人记得改列表"——而这恰恰是守卫最容易失效的方式。

（第二条测试 `TestOnlyTheDataLayerImportsDatabaseSQL` 是全仓扫描，所以 `database/sql` 那条规则没有这个问题；
只有"业务包不得碰 dal/dsm/dl"这条受影响。）

## 2. 修复：从目录树推导

`businessPackages` 遍历 `internal/` 下所有目录，排除 `db`（数据层本身）与 `arch`（它必须写出被禁包名），
再加上 `cmd`。附一条健全性断言：**至少找到 5 个包**，否则说明枚举逻辑坏了（比如路径写错），
不能让它悄悄通过。

## 3. 证明它能抓到

写一个临时包：

```go
package tmpprobe

import "github.com/easytier/easytier-console/internal/db/dal"

var Probe = dal.SQLite
```

`go test ./internal/arch/` 立即失败并点名：

```
architecture_test.go:38: internal/tmpprobe/probe.go imports .../internal/db/dal;
    business code must go through internal/db/bal
```

删掉后恢复绿。**这是本轮唯一的证据来源**——没有它，我改的只是一段看起来更好的代码。
