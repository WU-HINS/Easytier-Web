# 第 126 轮评审（2026-11-01）— 端口被占了，它说它起来了

R-B 第三轮：这次不是读代码，是在本机把守护进程**按运维的方式**跑两遍。

## 1. F-198（P1）绑定失败却打印"正在监听"，并且退出码 0

复现（端口 24111 已被另一个实例占用）：

    console listening on http://127.0.0.1:24111     <- 假的
    http server: listen tcp 127.0.0.1:24111: bind: address already in use
    central network reconciler started (interval 5s)  <- 进程还在跑
    shutting down / stopped                            <- 收到 SIGTERM 才退出
    exit code 0

三个问题叠在一起：

| 现象 | 后果 |
|---|---|
| 先打印 listening，后绑定 | 日志撒谎 |
| 绑定失败只打印一行，不退出 | 进程活着但不服务 |
| 退出码 0 | supervisor 认为是"正常停止"，不会重启也不会告警 |

在滚动重启、双副本同机、容器端口映射冲突这些场景下，这会变成一个**安静的死服务**。

## 2. 修法

    httpListener, err := net.Listen("tcp", opts.listenHTTP)
    if err != nil { return fmt.Errorf("http listener: %w", err) }
    ...
    log.Printf("console listening on http://%s", httpListener.Addr())

先绑定、再宣告、后服务。绑定失败直接返回，退出码 1。

## 3. 加一条门禁（第 21 项）

`scripts/check-port-conflict.sh`：起一个实例占住端口，再起第二个，断言三件事——

1. 第二个实例**非零退出**；
2. 它的日志里**没有** "console listening"；
3. 它的日志里**有** "address already in use"。

探针（把绑定错误吞掉、改绑随机端口）后，三条断言同时失败：

    the second instance kept running with no HTTP server
    the second instance claimed to be listening
    the failure was not reported as a bind conflict

## 7. 判断

这一类缺陷（"看起来成功，实际没做事"）在日志里最难识别：它不报错、不崩溃、退出码漂亮。
只有把进程真的跑起来、再人为制造冲突，才会露出原形——
这也是为什么"从 0 部署"必须包含**失败路径**。
