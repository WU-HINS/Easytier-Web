# 第 98 轮评审（2026-11-01）— 状态码也只被记录，不被断言

r95 处理了"匹配太松"，r96 处理了"只记录不判断空"。这轮看同一类还剩哪些：
**会变更状态的调用，状态码只被打印成表格里的一列。**

## 1. F-166（P2）四行"记录了等于没记"

| 行 | 记录的内容 | 之前有没有断言 |
|---|---|---|
| member added | 204 | 无 |
| member renamed | 204 | 无 |
| member override set | 204 | 无 |
| member renamed for ws | 204 | 无 |

如果路由被改坏、返回 404 或 500，走查会把 "404" 打印成一列继续跑完——
只有后续某条断言碰巧失败才会暴露。

## 2. 修法：require_code

    require_code "member renamed" 204 "$RENAME_CODE"

与上一轮的 `require()` 一样，只是判据从"非空"换成"等于期望值"。

## 3. 证明它能红（这次折腾了三次）

| 尝试 | 结果 |
|---|---|
| 改文件里**最后一个** 204 | 改到了别的 handler，冒烟照旧 PASS |
| 用 `index(chr(10)+"func ")` 切函数体 | 生成脚本时换行被 JS 模板吃掉，python 语法错误，变异没执行 |
| 用 chr(10) 正确切分后再改 | `FAIL: member renamed returned 200, expected 204` |

前两次都是"变异没生效却看起来像验证过"——**这正是本轮要防的失效模式**，
所以每次变异后都先 `grep -c` 确认文件真的变了，再跑冒烟。

## 4. 现在冒烟里的三类判据

| 辅助 | 判据 | 用在 |
|---|---|---|
| `step()` | 只记录 | 观察性输出（设备日志摘录等） |
| `require()` | 非空 / 最小长度 | 安全头、SPA 资源、设备注册 |
| `require_code()` | 等于期望码 | 会变更状态的四个调用 |

读脚本的人一眼能看出哪一行会拦人，哪一行只是打印。

## 7. 判断

"记录"与"断言"的边界，是这份冒烟脚本反复出问题的地方：三次不同形态（空值、宽松匹配、状态码）。
现在三类判据分开之后，新加一行时选择哪个辅助函数本身就是一次自我审查。
