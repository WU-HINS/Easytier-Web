# 第 18 轮评审（2026-11-01）— 把端到端接进冒烟

r17 的结论是"下一步必须让冒烟覆盖设备上线→配置下发"。本轮做完了这件事，
并且**它当场就找到了两个脚本层面的坑**。

## 1. 新增：假设备客户端

`cmd/smokedevice` 是一个最小设备：连控制面、发心跳、注册
`RunNetworkInstance` 处理器、等配置；收到就打印 `CONFIG_RECEIVED` 并以 0 退出，超时非 0。

冒烟脚本因此多了四步：

```
device registered   {"machines":[{"machine_id":"9a7c0000-...","hostname":"smoke-device"}]}
network created     9f08d958-ee2e-4b8c-81bc-0456e7b61a51
member added        204
config pushed       CONFIG_RECEIVED
```

服务端同期日志：`reconcile: pushed=1 skipped=0 failed=0`。

**这条链路如果断了，冒烟直接失败**——也就是说 F-041（对账循环没启动）这种
"实现了、测过了、没接上"的问题，以后会在 CI 第一步被拦住，而不是靠我第 17 轮偶然看一眼代码。

## 2. 过程中被冒烟自己抓到的两个坑（F-044）

| 现象 | 根因 |
|---|---|
| 设备启动即退出 | `--timeout 45` 缺单位；Go 的 `flag.Duration` 要求 `45s` |
| `member added 400` | 请求体里的引号转义在脚本里被吃掉，JSON 变成非法；而脚本把响应丢进 `/dev/null`，失败没有任何提示 |

第二条尤其典型：**冒烟脚本把关键步骤的输出丢掉，等于自己把自己变成瞎子**。
现在成员添加会打印状态码，失败时还会把设备日志与服务端日志一起打出来。

## 3. 门禁变化

`deploy smoke%% 这一步现在多花约 8 秒（等对账周期），但换来的是**整条链路**的证据：

```
== deploy smoke   PASS   (初始化 → 登录 → 注册 → 头 → WS → 设备注册 → 建网 → 加成员 → 收到配置)
```

## 4. 仍未覆盖

- 假设备只验证"收到配置"，没有验证**配置内容正确**（虚拟 IP、hostname 之外的字段）。
  下一步可以让 smokedevice 断言 `virtual_ipv4` 与网络意图一致。
- 没有验证"改动意图后配置会重新下发"（revision 变更路径只在单测里覆盖）。
