# 第 158 轮评审（2026-11-01）— 让"重复投递"这件事在真实传输上发生一次

上一轮让设备真的走了一次 UDP。这一轮补它的孪生问题：
**去重是不是真的在真实数据报上生效？**

## 1. 之前的证据不够

去重有三条用例，但都是在 Mux 内部"手工喂包"——直接调用未导出的 feed。
它们证明的是"判重函数是对的"，不能证明"在 UDP 上重复投递的同一帧会被挡住"。

中间还隔着：帧解析、隧道合成、accept、Run 循环，以及"这条隧道到底有没有声明自己是数据报"。

## 2. 新用例

TestDuplicateRequestOverUDPServerRunsOnce：

1. 起真实 ListenUDP 与 DialUDP；
2. 发第一帧（必须发，否则监听器不会合成隧道），然后 accept；
3. **先断言 accept 到的隧道 IsDatagram() 为真**——这是去重开关的依据，之前没人验过；
4. 再发同一帧（同事务 id），等一会儿；
5. 断言处理器只执行一次。

探针把 Dedupe 关掉：

    handler ran 2 time(s) for one request delivered twice

## 3. 这条用例补的是"层与层之间的缝"

| 层 | 已有证据 | 本轮补齐 |
|---|---|---|
| 判重逻辑 | 有（手工喂包） | — |
| 帧解析 | 有（wire 单测） | — |
| 隧道声明数据报语义 | 无 | 有（IsDatagram 断言） |
| 真实重复投递 | 无 | 有（同帧发两遍） |

## 4. 台账

248 项：240 FIXED / 8 ACCEPTED / 0 MONITOR / 0 OPEN。

## 5. 判断

这一轮没有改产品代码，只加了一条用例。但它把一个一直存在的假设
（"隧道会声明自己是数据报，所以去重是开着的"）变成了断言。

这类"层与层之间的缝"最容易长期没人管：每一层单独看都有测试，合起来的那条路径却没有。
上一轮和这一轮各补了一条缝（设备会话、重复投递），UDP 这条链路现在的证据是完整的。
