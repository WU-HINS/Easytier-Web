# 第 243 轮评审（2026-11-01）— storm 用例：不是超时太短，是两个假设不成立

F-307 我一直记成「固定 10s 截止太短」。读了测试才明白真正的问题有两个：

1. **UDP 会丢包，而每个 peer 只发一次有效帧**。丢一个包那个 peer 就永远不出现，循环一直等到截止；
2. 整个接受循环**共用一个 10s 窗口**，机器慢就累积超时。

## 1. 改法

- 每个 peer 每 50ms 重发有效帧，直到测试说停（done 通道）；
- 接受循环改成**每次 accept 一个 5s 独立截止**：真卡死仍然报错，慢机器不再误报。

这没有放松断言：垃圾帧照样先发，12 个 peer 照样必须全部到齐，race 检测照样开着。

## 2. 中途踩的坑

第一版改完直接跑满 120s 超时——因为我在 accept 循环**之前**保留了 wg.Wait()，
而 peer 现在要等测试结束才退出：**经典死锁**。把 wg.Wait() 挪到 close(done) 之后才对。

写并发测试时「谁等谁」的顺序必须重排，不能只改一半。

## 3. 证据

| 场景 | 结果 |
|---|---|
| 单跑 | ok 0.005s |
| 50 次 | ok 0.054s |
| race ×10 | ok 1.041s |
| 整个 wire 包 ×3 | ok 1.829s |
| **8 个 CPU 打满 ×10** | **ok 0.057s**（原条件下正是这会红） |

## 4. 结论

gate 里那条「偶发红」不再需要靠「停掉演示进程」来规避。
