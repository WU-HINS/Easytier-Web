# 第 72 轮评审（2026-11-01）— 七十个接口用例，从来没在 PostgreSQL 上跑过

"支持 SQLite 与 PostgreSQL" 是这套重写的核心需求之一。但检查下来：

> db 层有双方言用例，而**整个 REST 套件（70+ 用例）只在 SQLite 上跑**。

门禁里那条 postgres tests 跑的是 `go test ./internal/db/... ./internal/httpapi/...`，看起来覆盖了 API——
但 httpapi 的 harness 写死了 SQLite，所以那条命令只是"在 PostgreSQL 存在的情况下又跑了一遍 SQLite 用例"。

## 1. F-130（P1）让 harness 会说两种方言

设置 `EASYTIER_HTTPAPI_PG=<dsn>` 时，每个用例建一个**私有 schema**，通过 `options=-c search_path=...` 连进去，用完删掉。

第一版把 cleanup 写成 `defer`，于是 schema 在 harness 返回时就被删了——所有用例报 `relation "settings" does not exist`。
**这是"测试自己的 bug"的典型样子**，改成 `t.Cleanup` 后立刻正常。

结果：**70+ 用例在 PostgreSQL 上全绿**（28.6s）。

## 2. F-131（P1）顺手挖到 schema 硬编码

打通 PG 模式时发现 dsm 的内省把 schema 写死成 `public`：

    SELECT tablename FROM pg_tables WHERE schemaname = 'public'
    SELECT column_name FROM information_schema.columns WHERE table_schema = 'public' AND table_name = $1

在 search_path 指向自定义 schema 的库里（共享实例常见），控制台会**看到 public 下别人的表**，
判定"schema 已就绪"，然后运行期报 `relation "settings" does not exist`——或者更糟，把数据写进别人的表。

改用 `current_schema()`（与不限定 schema 的 DDL 使用同一目标）。

这个 bug 只有在"跑第二遍方言"时才会暴露——**它本身就是本轮结论的证据**。

## 3. F-132（P2）两条架构守卫口径不一致

架构测试里"只有数据层能 import database/sql"这条没排除 `_test.go`，而另一条早就放开了。
我为建 schema 引入 `database/sql` 就撞上了。统一口径后，自测确认**两条守卫仍然会抓到生产文件**。

## 6. 判断

"支持两种数据库"这句话，在 r72 之前只对 db 层成立。现在 API 层也有跨方言证据——
而且**第一次跑就抓到一个只在第二种方言下才出现的真实 bug**。

这就是为什么值得为方言差异单独跑一遍：不是形式主义，是因为差异真的存在。
