# 第 208 轮评审（2026-11-01）— 一个 padding 字节，卡住整个 2.6.4

上一轮把 2.6.4 的 udp 记成 FAIL 而没有猜原因。这一轮加了按包打印（EASYTIER_UDP_DEBUG），一次就看到了真相：

    wire: rejected datagram len=94  head=d0aae06803695600

拆开 8 字节头：conn=0x68e0aad0、type=3、padding=0x69、len=0x0056。
长度与总长完全自洽，唯一"不合规"的是那个 padding 字节——而我的解析器写了 data[5] != 0 就丢弃。

## 1. 结论

padding 是保留字节，不是哨兵。去掉这条约束后：

| 版本 | udp |
|---|---|
| 2.4.0 | PASS |
| 2.5.0 | PASS |
| 2.6.4 | PASS（连跑两次） |
| 2.7.0 | PASS |

整矩阵 10/12，只剩 2.4.0 / 2.5.0 的 ws（F-278）。

## 2. 用例与探针

TestEasyTierUDPSessionHandshake 现在同时发非零 padding 的 Syn（0x69）与 Data（0x61）。
探针把 data[5] != 0 加回去 → no sack came back。

## 3. 判断

同一类错误在这个项目里出现了很多次：把"我以为是常量"的字段当成校验条件。
名字叫 padding 的字节就该被忽略，按名字理解比按示例反推可靠。
