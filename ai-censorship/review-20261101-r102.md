# 第 102 轮评审（2026-11-01）— 越权矩阵只认识五个端点

这轮回到 R-F（越权）。先把公开面列出来，再看管理面是怎么被守住的。

## 1. 公开面清点（未套 requireUser / requireAdmin 的路由）

| 路由 | 为什么可以公开 |
|---|---|
| `GET /`、`GET /healthz` | 静态页与存活探测 |
| `GET /api/v1/setup`、`POST /api/v1/setup` | 首装入口，本身受 initialized 与令牌约束 |
| `POST /api/v1/auth/login`、`logout`、`register` | 认证入口，注册受开关与策略约束 |
| `GET /api/v1/auth/oidc/{config,login,callback}` | OIDC 三段，靠 state/nonce/PKCE 自证 |
| `GET /@up/{username}` | 设备通道，凭 token 在心跳里自证 |

清点结果：没有"应该受保护却没保护"的路由。

## 2. F-170（P2）管理面只被五条硬编码用例守着

越权矩阵（`TestPrivilegeMatrix`）逐个断言五个管理端点对普通用户返回 403。
但它是一张**手写清单**：新增第六个 `/api/v1/admin/*` 路由却忘了套 `requireAdmin`，
没有任何测试会红——契约检查只比对"客户端有没有调用"，不比对"有没有守卫"。

## 3. 修法：读路由源文件，不读清单

`TestAdminRoutesRequireTheAdminWrapper` 扫描 `internal/httpapi/router.go`：

    s.mux.HandleFunc("GET /api/v1/admin/users", s.requireAdmin(s.handleAdminListUsers))

凡注册在 `/api/v1/admin/` 下的 HandlerFunc，必须同时出现 `s.requireAdmin(`，
并要求**扫描到的管理路由不少于 5 条**——否则以后有人重构路由写法，这条检查会静默空转（r92 的教训）。

负向自测：把 `GET /admin/users` 的外壳去掉，立刻报

    admin route is not wrapped in requireAdmin: s.mux.HandleFunc("GET /api/v1/admin/users", s.handleAdminListUsers)

## 4. 写这条用例时踩的坑（都出在跨语言模板上）

| 现象 | 原因 |
|---|---|
| `undefined: repoRoot` | 新文件写成 `package arch_test`，而现有用例是 `package arch` |
| `undefined: chr` | 生成脚本时把 python 的换行写法漏进了 Go 源码 |

两次都由 `go vet` 立即指出，没有带进运行期。

## 7. 判断

越权这类问题最怕"清单式防护"：清单会过期，而源文件不会。
