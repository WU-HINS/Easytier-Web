# 第 10 轮评审（2026-11-01）— 换前提：多副本共库

本轮压的是架构里最后一个没被验证过的隐含假设：**控制台是单进程**。

## 1. 先取证：多副本共库到底会发生什么

`TestMultiReplicaConsistency` 用两个 `bal.Store` + 两个 `httpapi.Server`
指向同一个数据库，模拟"两个进程共库"：

| 检查 | 结果 |
|---|---|
| 在 A 初始化的会话，拿去请求 B | ✅ 200（会话在数据库里，跨进程可用） |
| 设备连到 A 后，A 的 `/machines` | ✅ online=true |
| 同一请求打到 B | ⚠️ 设备行在，但 **online=false** |
| 从 B 发起 `proxy-rpc` | ⚠️ **404**（隧道只在 A 的进程内存里） |
| 从 A 发起同样的 `proxy-rpc` | ✅ 正常（证明差异来自拓扑而非权限） |

**结论（F-028，P1）**：会话层天然可横向扩展，**设备控制面不是**。运维只要起两个副本挂到同一个 LB 上，
就会得到"一半请求里设备离线、设备操作随机 404"的诡异现象，而且**没有任何日志提示**。

## 2. 缓解：让多副本变成"响的失败"

不做分布式会话迁移（那是重架构），先消除**静默**：

- 新增声明式表 `console_instances`（id / version / started_at / last_seen + last_seen 索引）。
- 进程启动即写入一行，之后每 5 秒随心跳刷新。
- 每轮统计 30 秒内有心跳的实例数，**>1 就打一条明确的 WARNING**：

```
WARNING: 2 console instances share this database; device tunnels are per process,
so device control and online state are NOT shared
```

- `TestInstanceHeartbeatDetectsReplicas`：两个 Store 共库 → 双方都读到 2；重复上报只更新不新增。

这样部署者第一时间就能知道"你正在做一件这版架构不支持的事"，而不是靠用户投诉"设备时好时坏"。

## 3. 未做的部分（明确记录）

- 真正的多副本支持需要：设备隧道归属表 + 跨副本路由（或按设备粘性路由）。
  这是架构级改造，不在评审轮次内夹带。
- 没有做"检测到多副本就拒绝启动"：只告警不阻断，避免把正在运行的实例踢下线。
