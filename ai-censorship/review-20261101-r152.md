# 第 152 轮评审（2026-11-01）— 反射面与去重的最后两处

第三轮团队留下的六条，这轮再收两条。

## 1. F-241：未绑定的会话不该拿到任何回答

getFeature 在注册时就进了注册表，而 mux 在分发前**不看会话是否已绑定**。
配合 UDP（源地址可伪造），这个端口就成了反射器：一个伪造源的数据报，换来一个发往受害地址的应答。

修法：处理器外面包一层 bound 检查，未绑定直接返回 session: not bound yet。
未绑定之前，任何 RPC 都不会被应答。

## 2. F-244：分片请求的去重从来没生效过

上一轮把单包请求纳入了去重，但多分片的仍然不行：

    完成时 remember(p) 记录的是"最后到达那片"的长度
    重传时最先到达的是第 0 片（满片）
    长度不等，判为新请求，整单重跑

而且 size 从语义上就不该参与判断：它记录的是分片长度，而重传是逐片到达的。

修法：去掉长度比较，键改为"对端 + 事务 id + 2 秒窗口"。这是 r148 那次误伤之后的第二次调整——
第一次只有 id，误伤合法复用；第二次加了长度，等于让多分片永远命中不了。
现在是**对端 + id + 时间窗**，既不会误伤，也不会漏判。

## 3. 证据

TestMultipartRetransmissionIsAlsoDeduped：两片各重传一次，合并结果只投递一次。
探针去掉 remember 后：

## 5. 判断

这两条都属于"我上一轮以为修好了"。F-244 尤其典型：
r148 的修复通过了所有用例，因为我为它写的用例恰好是单包的；
而真正需要去重的多分片路径，从头到尾没被验证过。

去重这件事在这个项目里改了三次才对——每次都是"看起来对"，
每次都是用例的形状决定了它看起来对。

## 6. 补记：这一轮我又自己制造了一个回归（F-246）

把"分片去重"改成"对端 + id + 2 秒窗口"之后，门禁红了：

    == postgres api   FAIL
    --- FAIL: TestProxyRPCListRouteEndToEnd
        list_route = 500 internal error

原因：去重是**无条件**的，而事务 id 只在**单个对端**内唯一。
控制台自己发起的 proxy-rpc 调用（每次 mux 从 1 开始编号）被服务端当成了重复请求丢掉了。

这和 r148 那次是同一个错误的两个面：**我总在去重上忘记 id 的作用域**。
最终的修法不是再调键，而是把开关放到正确的位置——
rpc.Options.Dedupe 默认关闭，只有 udpTunnel（实现了 IsDatagram）才打开：

    数据报：可能重复投递 → 去重
    流式：不可能重复交付 → 不去重

只有需要它的传输层才承担它的风险。这条比前面三次调键都更接近本质。
