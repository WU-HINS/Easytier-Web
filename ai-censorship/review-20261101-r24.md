# 第 24 轮评审（2026-11-01）— 设备操作接口：先证明它能用

r23 的结论是"下一个高价值项是 `proxy-rpc` 的设备操作界面"。动手前先做了一件更基本的事：
**证明这条链路真的通**。结果发现它只在部分方法上通。

## 1. F-059（P2）proxy-rpc 从来没有端到端用例

此前关于 `proxy-rpc` 的断言只有两类：未知方法 400、设备不在线 404。
"控制台 → 设备 → 把结果序列化成 JSON 返回"这条主链路**没有一条用例**。

本轮补上 `TestProxyRPCListRouteEndToEnd`：假设备注册
`api.instance.PeerManageRpc#3`（ListRoute），返回一条 route，
断言控制台代理回来的 JSON 里 `routes[0].hostname == "peer-a"`。**通过**。

顺带确认了一个容易写错的细节：服务名要按**最后一个点**切分，
即 `api.instance.PeerManageRpc` → key=`api.instance` + name=`PeerManageRpc`，
设备侧注册时必须用同样的切分（我第一次写成 key=`api`，设备回了 `InvalidMethodIndex`）。

## 2. F-058（P2）三个白名单方法根本不可用

方法索引由上游 .proto 生成，entries 有几十条；但 Go 侧只生成了其中一部分 message。
`newMessage(%s)` 找不到类型时返回错误，接口层把它当成 500 内部错误抛出去：
前端看到的既不是"不支持"，也不是"设备问题"，而是"服务器炸了"。

实测不可用的是三个：`ConfigRpc.GetConfig`、`ConfigRpc.PatchConfig`、
`ConfigRpc.GetLoggerConfig`。实例管理那一批（ListRoute / ListPeer / ShowNodeInfo …）**是可用的**。

**修复**：

- `methodAvailability` 用 `protoregistry.GlobalFiles` 检查入参/出参 message 是否真的存在；
- 不可用时返回 **400**，文案是"… is not available in this build: message X was not generated"；
- 新增 `GET /api/v1/rpc-capabilities`，逐服务逐方法返回 `available` 与原因，
  前端据此**隐藏**不可用动作，而不是点一下才失败。

## 3. 为什么这轮没有直接做界面

设备操作界面依赖 `ListRoute` 的返回结构。先把"结构长什么样、错误怎么表达"钉死，
再做界面，才不会出现"UI 写完了接口不对"的返工（r19 的编辑接口、r22 的成员面板都吃过这个亏）。
下一轮做界面时，形状已经是确定的。

## 4. 剩余的真实缺口

- 三个 config 方法需要补 .proto 代码生成（当前环境没有 `protoc`），登记为待办；
- 前端尚未使用 `/rpc-capabilities` 与 `proxy-rpc`（契约检查里仍列为未调用路由）。
