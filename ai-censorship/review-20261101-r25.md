# 第 25 轮评审（2026-11-01）— 路由表界面与 payload 契约

r24 把 `proxy-rpc` 的形状钉住了，本轮据此把界面做出来，并把 payload 也钉死。

## 1. F-061（P2）payload 形状没有断言

proxy-rpc 的请求体是 protojson：`{"instance":{"id":{"part1":..,"part4":..}}}`。
一旦前端把 UUID 拆错（例如当成字符串传、或字节序搞反），设备侧要么把它当默认实例、
要么静默用错实例——**两个都是最难查的那类问题**。

本轮在 `TestProxyRPCListRouteEndToEnd` 里让假设备把收到的 instance id 回显出来，
断言与请求一致（`part1=10` → 设备看到 `0000000a00000000`）。写这条断言时我第一次把
期望值算错了（把四个 part 的拼接顺序想反），测试立刻纠正了我——这正是它该起的作用。

## 2. F-060（P2）设备路由表界面

新增 `DeviceRoutes` 面板：

- 设备行里多一个"路由表"按钮，展开后可选**具体的网络实例**（一台设备可能跑多个网络）；
- 表格列：节点 ID / 主机名 / 虚拟地址(带前缀) / 跳数 / 路径延迟；
- 虚拟地址由 `Ipv4Inet{address{addr},network_length}` 还原成点分四段，**不在前端做任何猜测**；
- 面板先读 `/rpc-capabilities`：当前构建不支持 ListRoute 时直接显示原因，而不是给一个点了就 500 的按钮；
- 设备离线或没有运行实例时给出对应提示，不发请求。
