# 第 203 轮评审（2026-11-01）— 2.4.0 到 2.7.0 全部接通，靠的是键名和一个被证伪的"改进"

## 1. 真正的根因：proto_name 不是包名

上游生成的服务 descriptor 把服务名写了两遍。证据来自客户端自己的心跳：

    descriptor: RpcDescriptor { proto_name: "WebServerService", service_name: "WebServerService" }

所以它自己的服务键是 proto_name == service_name == "WebClientService"，
而我们一直发 proto_name "api.manage"——那是**包名**。客户端按三元键精确匹配，于是每次下发 InvalidService。

改成 ProtoName == "WebClientService" 之后：

| 版本 | 设备上线 | 白名单并网 | 下发 | 客户端 |
|---|---|---|---|---|
| 2.4.0 | ✅ | ✅ | pushed=1 | instance started |
| 2.5.0 | ✅ | ✅ | pushed=1 | instance started |
| 2.6.4 | ✅ | ✅ | pushed=1 | instance started |
| 2.7.0 | ✅ | ✅ | pushed=1 | instance started |

（沙箱没有 CAP_NET_ADMIN，实例随后报 tun 权限错误——这恰好证明配置真的到达并被执行。）

## 2. 一个"改进"被自己的测试推翻

我顺手把 GetFeature 改成"绑定前也回答"，想让客户端别降级到 legacy tunnel。结果 2.6.4 与 2.7.0 **反而连不上**了。
回退后立刻恢复。结论：legacy 降级目前是 load-bearing 的，我们返回的 GetFeatureResponse 与客户端期望不符。
已回退并把这条写进注释与台账（F-274 ACCEPTED）。
