# 第 9 轮评审（2026-11-01）— 换前提：生产 TLS 拓扑

上一轮结论是"别重复扫同一批路径，换前提再压"。本轮换的前提是**生产 TLS 部署**：
此前 8 轮的每一个用例都跑在 `SecureCookies=false` 的明文 HTTP 上，
而生产一定是 TLS + Secure Cookie。这条路径没有实证。

## 1. 新增覆盖（F-026，证据缺口）

`internal/httpapi/tls_test.go` 用 `httptest.NewTLSServer` 起真实 TLS 监听：

| 用例 | 断言 |
|---|---|
| `TestSecureCookieOverTLS` | 初始化后 `Set-Cookie` 同时含 `Secure`、`HttpOnly`、`SameSite=Lax`、`Path=/`；Cookie 能认证后续请求；安全响应头在 TLS 监听上同样存在 |
| `TestSecureCookieIsNotSentOverPlainHTTP` | 同一个 jar 面对 http origin 时不提供 Secure Cookie（证明该标志真的在保护会话） |
| `TestOIDCLoginDerivesHTTPSRedirectOverTLS` | TLS 监听下未传 `redirect_url` 时，授权请求的 `redirect_uri` 推导为 **https** 且路径固定为 `/api/v1/auth/oidc/callback` |

### 一次"测试写错、产品没错"的经历

第一版断言读的是 `cookiejar.Cookies()` 返回的 Cookie 结构体，结果报"缺少 Secure"。
排查后发现是 **Go 的 cookiejar 在回传时会丢掉 Secure/HttpOnly/SameSite 等属性**——它只保证
name/value/domain/path。也就是说断言测的是 jar 的行为，不是服务端发出的头。

改为直接解析响应里的 `Set-Cookie` 原始头后通过。**没有改产品代码**：
先确认是测试的问题，再改测试。这条记下来，是因为"测试红了就改代码"是最常见的误伤。

## 2. 新登记：F-027 反代场景的默认回调推导（P2，MONITOR）

TLS 由反向代理终止时，到进程的连接是明文，`r.TLS` 为 nil：
- 若前端显式传 `redirect_url`（当前前端 **总是** 这么做，见 `oidcCallbackURL()`），校验走 https 分支，正确；
- 若调用方省略该参数（例如脚本直连），默认会推导成 `http://...` 并被拒绝。

**当前不修**：产品路径（浏览器）永远带参数；改服务端信任 `X-Forwarded-Proto` 会引入新的伪造面
（除非同时引入可信代理白名单）。登记为部署约束 + 后续增强项。
