# 第 15 轮评审（2026-11-01）— 换前提：数据竞争

本轮把整套测试放到 `-race` 下跑。这是我把它推迟到第 15 轮的唯一原因：慢。
结果是**三个问题，两个在代码里，一个在测试里**。

## 1. 第一次 -race 结果

```
internal/rpc   FAIL: TestFrameStaysWithinMTU (race detected)
```

报告指向 **测试代码**：`maxSeen` 在采集 goroutine 里写、在主测试里读。
用 `atomic.Int64` 修正。**产品代码在这一处是干净的。**

## 2. 修完再跑，冒出更严重的一组

`TestConcurrentSetupCreatesExactlyOneAdmin` 在 `-race`（更慢的时序）下开始失败。
把用例改成统计**状态分布**之后，问题暴露得很难看：

```
status distribution = map[-1:8]
  bodies[-1] = context deadline exceeded (Client.Timeout exceeded while awaiting headers)
```

根因不是竞态，是**成本**：每个 `/setup` 请求在 CAS 之前先做一次 argon2（64 MB、4 线程）。
8 个并发请求 = 512 MB 峰值 + CPU 打满，叠加 SQLite 单写者，直接把 10 秒客户端超时打穿。

顺着这条线查出 **F-037（P1）**，它不是"测试太慢"，是真实攻击面：

- **无并发上限**：未认证调用者可以用登录接口把 argon2 并发拉满（内存放大）；
- **限流键含用户名**：轮换用户名即可绕过（每 IP 只有 10 次/用户名）；
- **未知用户名不计入失败**：更好打——连桶都不进，且不消耗 argon2（顺带形成**用户名枚举的时间侧信道**）。

## 3. 修复

| 问题 | 修法 |
|---|---|
| 计算放大 | `internal/auth` 增加全局哈希信号量（上限 4） |
| 用户名轮换绕过 | 限流增加**每 IP 独立桶**（30 次 / 5 分钟） |
| 未知用户免费尝试 | 未知用户同样计入失败桶，并对一个固定假哈希做一次 `Verify`（等时） |

回归：`TestLoginThrottleIsPerAddressToo`（31 次轮换用户名 → 429）、`TestLoginIsThrottled`（原用例仍通过）。

## 4. 测试自身的问题（F-039）

原用例在 goroutine 里调用 `t.Fatalf`——Go 明确不允许：它只终止那个 goroutine，
测试会"看起来跑完"，失败被吞掉。这就是为什么最早那次红灯只显示 `conflicts = 6, want 7`
而看不出到底是哪个请求异常。新增 goroutine-safe 的请求助手后才看到 `context deadline exceeded`。

**教训**：并发用例里任何 `t.Fatalf` 都是隐患，必须把错误**返回**到主测试再判定。
