# 第 31 轮评审（2026-11-01）— 故障隔离

r30 的结论指向"错误文案的可操作性"。查文案的时候顺手看了一眼前提：**错误发生后，别的东西还能不能继续跑**。
答案是：不能。

## 1. F-072（P1）一个坏网络能让整个租户停摆

`ReconcileUser` 里：

```go
plan, err := Compile(network, members, byID, credentials)
if err != nil {
    return report, fmt.Errorf("central: compile network %s: %w", network.ID, err)
}
```

一个网络编译失败 → 直接 return → **该租户剩下的网络这一轮全都不下发**；
再往上一层，`ReconcileAll` 遇到某个租户返回错误也会 `return`，**其他租户一起停**。

而"编译失败"在生产里并不罕见：r20 之前写入的脏策略、子网耗尽、成员地址越界，都会走到这里。
表现是"某些设备莫名其妙不再更新配置"，日志里只有一行 reconcile failed。

**修复**：

| 位置 | 改动 |
|---|---|
| `ReconcileUser` | 编译失败 → `report.CompileErrors++` + 记一条带 network id 的日志，`continue` |
| `ReconcileAll` | 单个租户出错 → `total.Failed++` + 日志，继续下一个 |
| `Report` | 新增 `CompileErrors` 字段，汇总日志变成 `pushed/skipped/failed/compile_errors` 四项 |

**回归** `TestBrokenNetworkDoesNotBlockOthers`：一个正常网络 + 一个策略损坏的网络（直接写库模拟历史脏数据），
断言 `ReconcileUser` 不返回错误、`CompileErrors==1`、正常网络的修订仍然被写入。
改前该用例在第一步就会因为返回错误而失败。

## 2. F-073（P2，ACCEPTED）错误文案抽查

返回 400 时的文案抽查（都在编译错误路径上）：

- `unknown acl selector type "cidr"`
- `member 3333... address 10.99.99.99 is outside the network subnet 10.30.0.0/29`
- `proxy cidr "10.0.0.0/33" is invalid`
- `networking_method Manual requires peer_urls or public_server_url`

都含字段名与具体取值，且在 `/networks/{id}/members` 的 `compile_error` 里返回、在成员面板上显示。
按"可操作性"标准检查通过，登记为 ACCEPTED（无需改动）。

## 4. 判断

这轮和 r17（对账循环没启动）是同一类问题的两个面向：**r17 是"没接上"，r31 是"接上了但一碰就全停"**。
分布式控制系统里，"局部失败必须局部处理"这条原则此前从未被显式检查过——现在有用例守着了。
