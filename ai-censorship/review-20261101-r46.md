# 第 46 轮评审（2026-11-01）— OIDC 绑定的接管路径

上轮收尾提的是"前端 `isSecureOrigin` 与服务端 `requestScheme` 是否一致"。核对结果是：
绑定流程**总是显式传 redirect_url**，服务端不推导，所以两者不会打架——这条担心不成立。

但顺着绑定流程看下去，发现更要紧的东西：**这条路径一个用例都没有**。

## 1. F-095（P1）账号接管守卫没有证据

`handleOIDCCallback` 里，绑定模式只有一行保护：

```go
if bag.Mode == "bind" {
    session, err := s.requireSessionUser(r)
    if err != nil || session.ID != bag.UserID {
        writeError(w, http.StatusUnauthorized, "bind session does not match")
```

它挡住的是：**攻击者拿一份"为受害者签发"的 bind state，用自己的会话完成回调**——
如果这行失效，攻击者的 IdP 身份就绑到了受害者账号上（等于账号接管）。

新增 `TestOIDCBindRejectsForeignSession`：

| 步骤 | 断言 |
|---|---|
| 用测试密钥签发 `Mode=bind, UserID=受害者` 的 state | — |
| 以攻击者会话回调 | **401**，且响应文本是 `bind session does not match`（证明是守卫拦下的，不是 PKCE 或 state 校验顺带失败） |
| 检查受害者记录 | `oidc_subject` 仍为空 |
| 换成本人 UserID 重复一次 | 302 到 `/?bound=1`，且 `oidc_subject` 落库 |

第三个断言很关键：只看 401 不能区分"被正确的守卫拒绝"和"因为别的原因碰巧失败"。

过程中踩了两个坑，都记在这里：

- 假 IdP 的 PKCE 校验依赖 `Expect(nonce, challenge)`，伪造 state 时必须先把 challenge 注册进去，否则会以
  `pkce mismatch` 失败——**这正是"错误理由"的样子**；
- 未初始化的库会让登录直接 409，测试必须先 `MarkInitialized`。这两条都是"测试自己的陷阱"。

## 2. F-096（P2）清除 cookie 时属性不一致

设置 state cookie 时是 `Secure + HttpOnly + SameSite=Lax`，清除时只写了 `HttpOnly`。
浏览器按名字+路径删除，功能上没坏，但同一份 cookie 的两处定义不该不一样。已补齐。
