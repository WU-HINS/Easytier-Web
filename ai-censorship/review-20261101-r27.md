# 第 27 轮评审（2026-11-01）— 回到后端：把字节序钉死在协议上

r25 留了一条诚实的"未验证"：界面把 `Ipv4Inet.addr` 按"首字节是最高位"还原成点分地址，
但没有对真机或上游源码核对过。本轮把它查清楚，并且变成门禁的一部分。

## 1. 上游源码是唯一权威

`easytier-proto/src/common.rs`：

```rust
impl From<std::net::Ipv4Addr> for Ipv4Addr {
    fn from(value: std::net::Ipv4Addr) -> Self {
        Self { addr: u32::from_be_bytes(value.octets()) }
    }
}
impl From<Ipv4Addr> for std::net::Ipv4Addr {
    fn from(value: Ipv4Addr) -> Self {
        std::net::Ipv4Addr::from(value.addr)   // 大端解释
    }
}
```

`u32::from_be_bytes([a,b,c,d])` = `a<<24 | b<<16 | c<<8 | d`，也就是说
**首字节确实是最高位**——前端 `(addr>>24)&255` 的写法是对的。

顺带确认 UUID：`Ipv4Inet` 旁边的 `UUID` 同样是四个 `uint32` 大端，
和 proxy-rpc payload 里 `part1..part4` 的切分一致。

## 2. 把结论变成机器检查，而不是注释

新增 `client/src/lib/wire.ts`（无依赖，只放 `uuidParts` / `formatIpv4`），
`http.ts` 改为 re-export；新增 `scripts/check-wire.mjs`，用
`node --experimental-strip-types` 直接 import 这个 .ts 文件跑黄金值：

```
formatIpv4(0x0a636401, 24)  -> 10.99.100.1/24
formatIpv4(0xffffffff, 32)  -> 255.255.255.255/32
uuidParts("9a7c0000-...-000000000001") -> {9a7c0000, 00004000, 80000000, 00000001}
```

**验证器自身验证过**：把八位组顺序倒过来 → 输出 `1.100.99.10/24` 并 exit 1；改回 → 通过。

这也顺带解决了一个结构问题：之前这两个纯函数埋在 500 行的 `http.ts` 里，任何脚本都碰不到。
