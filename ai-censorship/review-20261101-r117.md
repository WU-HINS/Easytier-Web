# 第 117 轮评审（2026-11-01）— 一次假阳性，和一条真断言

这轮用手工演练验证"改密撤销会话"这条 r75 的设计：起真守护进程、两个 cookie jar 当两台设备。

## 1. 第一次演练：我自己错了

    A 改密（curl -b A.jar）→ 204
    A machines → 401
    B machines → 401

看起来像"调用方被自己的操作踢下线"。但问题在 curl：`-b` 只读 jar、不写，
改密响应里新下发的 cookie 没被保存，A 手里还是旧值——**服务器行为正确，测量方法错了**。

改成 `-b A.jar -c A.jar` 再跑：

    A machines → 200   （新 cookie 生效）
    B machines → 401   （另一台设备被撤销）

这条记在这里，是因为**"手工验证出的 bug"同样需要复核**，否则会浪费一整轮去修一个不存在的问题。

## 2. F-184（P2）真正的缺口：旧 cookie 没有被断言

现有用例断言的是"调用方还能用"和"其它会话被撤销"。
如果实现改成"删别人的、留自己的"，两条都会通过——而被窃取的 cookie 会活得比撤销动作更久。

新增 `TestRotationInvalidatesTheCallersOldCookie`：

1. 取注册时下发的 cookie 原值；
2. 完成改密；
3. 用**原值**直接重放请求 → 断言 401；
4. 同时断言调用方通过新 cookie 仍然 200。

## 3. 探针

把 `DeleteUserSessions` 短路后：

    --- FAIL: TestRotationInvalidatesTheCallersOldCookie
        the pre rotation cookie still works: 200
    --- FAIL: TestPasswordRotation
        another session survived the rotation

两条同时红，说明新用例补上的正是原来没人看的那一面。

## 4. 本轮验证

    探针                                                            FAIL（预期，两条）
    手工演练（真守护进程 + 两个 cookie jar）                         行为符合设计

## 6. 判断

同一件事有三个层次：**结果对不对**（还能不能用）、**副作用对不对**（别人失效了吗）、
**旧凭证是否彻底作废**。前两个一直有人看，第三个是这轮补的——而它恰好是安全上最要紧的那个。
