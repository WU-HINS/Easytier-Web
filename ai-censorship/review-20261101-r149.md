# 第 149 轮评审（2026-11-01）— 顺着"id 唯一"的假设往下查

上一轮的教训是"事务 id 只在单个 mux 内唯一"。这一轮顺着同一根线查：
**还有哪些地方默认了某种 id 或键是全局唯一的？**

## 1. 查了哪些

| 位置 | 键 | 结论 |
|---|---|---|
| rpc.Mux.pending（响应匹配） | transaction id | 每个 mux 自增，天然唯一，没问题 |
| session.Manager.sessions | (userID, machineID) | 语义就是"一台设备一条隧道"，有意为之 |
| managed_config_revisions | (user, device, network) | 三级键，没问题 |
| loginLimiter | 地址 + 用户名 | 见下 |

登录限流有一处已知取舍：trust_proxy 关闭时，所有经代理的请求共享代理 IP。
这是"要么共享桶、要么信任伪造头"的二选一，README 已写明只在该代理由你控制时才开。
这一轮不动它，但把它记在下面作为明确的边界。

## 2. 顺手清掉一个"看起来像基础设施"的死字段（F-236）

Server 上有个：

    mu      sync.Mutex
    private map[string]string // per-request scratch space for tests

全仓没有任何读写点。它带锁、有注释、看起来像"随请求传递的上下文"，
但**没有任何一行代码碰过它**。

这种字段的危害不是现在，而是将来：下一个想加缓存的人会直接往里写，
然后在一个每请求一个 goroutine 的服务里造出真正的数据竞争。删掉。

## 3. 本轮验证

跑的是**带引用证据扫描的全量门禁**（EASYTIER_FULL_GATE=1），
23 项含 cited tests：账本引用的全部用例必须真的运行、不得跳过。

## 5. 判断

这一轮产出很小——一个死字段加一次全量验证。但它回答了上一轮留下的问题：
**没有第二处犯同样的错**。事务 id 的坑是孤例，不是模式。

关于"删代码"：这个项目里删掉的东西（死名单、整行豁免、假检查、死字段）
比加进去的更值得记，因为**每一处删除都减少了一个将来会被误解的暗示**。
