# 第 52 轮评审（2026-11-01）— 升级路径：旧库 + 有数据

声明式 Schema 的对齐**每次启动都会跑**。此前测过两件事：空库建表（r8）、重复对齐幂等（r3）。
但没测过最危险的组合：**旧版本留下的库，里面有数据，缺一张表**。

## 1. F-105（P2）升级路径只在"空库"和"幂等"两端被验证过

真实升级长这样：上一版没有 `console_instances`（r10 才加），库里已经有一堆用户和网络，
新版本启动 → 对齐发现缺表 → 建表 → 继续跑。中间任何一步出错（例如建表顺序、外键、指纹变化导致重建）都是生产事故。

`TestMissingTableIsRecreatedWithoutDataLoss` 把这条路径演出来：

| 步骤 | 断言 |
|---|---|
| 建库 + 写一个用户和一个网络 + 关库 | — |
| `DROP TABLE console_instances`（模拟旧版本） | — |
| 重新打开 | 变更计划里有 `create_table console_instances` |
| | **指纹不变**（说明没有发生隐式重建） |
| | 用户与网络仍在、网络名未变 |
| | 新建的表可写（`TouchInstance` 成功） |

`TestMissingTableIsRecreatedOnPostgres` 跑同一条路径的 PG 版本——r8 出的正是这层 DDL 顺序问题
（子表先于父表创建，SQLite 容忍、PG 报错），所以两种方言都要有。

## 2. 为什么这条比"再补一个静态检查"更重要

门禁已经 14 项，其中一半是静态检查。静态检查保证"代码没有明显违反约定"，
但**升级路径的正确性只能靠真跑一次**：它涉及数据、DDL 顺序、指纹、外键，任何静态分析都看不到。

## 4. 判断

数据库这一层的风险排名：**升级 > 并发 > 新建**。因为升级发生在每个实例的每次启动，而且用户的数据就在里面。

现在三档都有用例了：新建（r8）、幂等（r3）、升级（本轮）。
