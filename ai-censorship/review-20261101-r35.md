# 第 35 轮评审（2026-11-01）— 组网方式的必填项，按上游校准

r34 收尾时留下一个问题：**Manual 模式我们是不是比上游严格**。读 `compile_mode` 后答案是：
不是严格，是**宽松在错的地方**。

## 1. 上游的三条规则

```rust
PublicServer { url } => validate_url(url)?                       // URL 必填且合法
Manual { peer_urls } => if peer_urls.is_empty() { Err(EmptyPeerUrls) }  // 只认 peer_urls
Gateway { peer_url } => validate_url(peer_url)?
Standalone => 无对端
```

对照我们的实现（r21 起的规则）：

| 模式 | 我们 | 上游 | 差异 |
|---|---|---|---|
| PublicServer | r34 起要求 URL | 要求 URL | ✅ 一致 |
| Manual | peer_urls **或** public_server_url | **只认 peer_urls** | ❌ 我们放行了上游会拒绝的组合 |
| Gateway | peer_urls 或 URL | 只要 URL | ❌ 同样放行了错组合 |
| Standalone | 无 | 无 | ✅ |

也就是说：一个"Manual + 只有 public_server_url"的网络，我们能建、能编译、能下发，
但上游语义里它是 `EmptyPeerUrls`，设备会拿到一个 Manual 模式却没有对端的配置——**孤岛**。

## 2. F-082 另一半：peer_urls 不排序不去的后果

上游对 peer_urls 做 `sort + dedup`，我们没有。后果很具体：
管理员把两个 peer 换个顺序，**编译结果变了 → 修订号变了 → 全量重新下发**。
配置没变，设备却收到一次 "配置更新"。

**修复**：`buildConfig` 里 `peerURLs = dedupeSorted(peerURLs)`。

回归 `TestPeerURLsAreSortedAndDeduped`：三个 URL（含重复）编译成两个且有序；重排同一集合结果不变。
