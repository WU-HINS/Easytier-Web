# 第 76 轮评审（2026-11-01）— 两个并发 setup，两个管理员

r72 让 REST 套件跑上了 PostgreSQL。这一轮，那条新通道**抓到一个 P1**。

## 1. F-137（P1）单管理员不是数据库约束

CreateAdmin 的实现是：

    INSERT INTO users (username, password, role, created_at)
    SELECT $1, $2, $3, $4
    WHERE NOT EXISTS (SELECT 1 FROM users WHERE role = $5)
    RETURNING id

看起来是原子的——**在 PostgreSQL 的 READ COMMITTED 下不是**：两个并发事务都在自己的快照里看到"还没有管理员"，
于是都通过检查、都插入。实测：

    --- FAIL: TestConcurrentSetupCreatesExactlyOneAdmin
        created = 2, want exactly 1; status distribution = map[201:2 409:6]

**两个请求都拿到了 201，系统里有两个管理员。**

SQLite 一直没暴露这个问题，因为它单写者串行化；而这条用例从 r2 起就在跑，跑了七十多轮。
换句话说：**只有真的把方言跑起来，才能看见它**。

## 2. 修复：让数据库说不

users 表加一个部分唯一索引：

    {Name: "uq_users_single_admin", Columns: []string{"role"}, Unique: true, Where: "role = 'admin'"}

SQLite 与 PostgreSQL 都支持部分索引。再让 CreateAdmin 把唯一冲突映射成 `ErrAdminExists`（新增 `isUniqueViolation`，
与既有的 `classifyInsertError` 同一套匹配），于是输的那一方得到 **409**，而不是 500。

## 3. 第一次写的用例是假绿的

我先写了个顺序用例（建一个管理员、再建一个，期望第二个失败），然后用"删掉索引"做负向自测——
**结果它照样通过**。顺序执行时 `WHERE NOT EXISTS` 本来就能拦住，这个用例证明不了任何事。

改成**直接问引擎**：

| 方言 | 查询 |
|---|---|
| SQLite | `sqlite_master WHERE type = index AND name = uq_users_single_admin` |
| PostgreSQL | `pg_indexes WHERE schemaname = current_schema() AND indexname = uq_users_single_admin` |

再删掉索引做负向自测，两个方言都报 `the single admin index is missing`。
同时保留行为级用例 `TestSecondAdminIsRefused`，以及原来的并发用例（PG 上连跑 15 次 0 失败）。

## 4. F-138（P2）新用例把老用例搞挂了

加完私有 schema 用例后，`TestPostgresBackupCommand`（r71 写的）开始失败。两个原因叠在一起：

1. 我的 cleanup 顺序错了——先 DROP SCHEMA 再关连接，DROP 等待连接而**静默失败**，schema 留在库里；
2. 那条断言查 `information_schema.tables` **没限定 schema**，把别的 schema 里的同名表当成了自己的。

修法：cleanup 改为"先关 store/raw/admin，再用新连接 DROP SCHEMA CASCADE"并记录失败；
断言加 `table_schema = current_schema()`。跑完确认 `single_/harness_/e2e_` 前缀的 schema 数量为 0。

**第二条尤其值得记**：r71 那条用例当时是绿的，但它依赖"整个库只有我自己"这个未声明的假设。
