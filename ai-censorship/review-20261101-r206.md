# 第 206 轮评审（2026-11-01）— udp 修好了：16 字节是会话头，缺的是一个 Sack

## 1. 从抓包到定论

上一轮抓到客户端每 3 秒重发的 16 字节：

    2b05df2c 01 00 0800 | 6e00d891 002de820

读上游 socket/udp/packet.rs 后确认它是 8 字节会话头：

| 字段 | 值 |
|---|---|
| conn_id | 0x2cdf052b (u32 LE) |
| msg_type | 1 = Syn |
| padding | 0 |
| len | 8 |

后 8 字节是 magic。服务端要做的事只有一件：**回一个 Sack（同 conn_id、同 magic）**，
然后 Data 帧就是 ZCPacket 本体。

## 2. 实现

- internal/wire/et_udp.go：会话头编解码；
- udpListener.handleEasyTier：Syn→Sack、Data→Packet、Fin→forget，Syn 到达即接受会话；
- 出站按会话头封装（msg_type=3, len=body）；
- 与自家 4 字节长度帧共存：靠 msg_type 与 len 的一致性做判定，两者互不吞并。

## 4. ws 的老版本缺口（F-278）

2.6.4 / 2.7.0 的 ws 正常；2.4.0 与 2.5.0 连上来后立刻 1006 断开。已经让服务端在无路径的 / 与 /ws 上接受升级
（它们不带 /@up/<user>），仍不通，说明差别在帧或子协议上，留作下一轮。

## 5. 判断

这一轮是"读源码 + 抓包"直接换来了功能：16 个字节，一个 Sack，四种版本全通。
