# 第 148 轮评审（2026-11-01）— 我上一轮自己标出来的空白

上一轮的结论里，我写过一句"没找的：UDP 上层 RPC 的重复执行"。
这一轮就去填这个洞——因为 UDP 会重复投递，而我一直假设 RPC 层不在乎。

## 1. 假设被推翻（F-235）

重组器看起来做了去重：

    if entry.pieces[p.PieceIdx] == nil {
        entry.pieces[p.PieceIdx] = ...
        entry.received++
    }

但这段只在**重组项还活着**的时候有效。单分片请求一收到就 received == totalPieces，
立刻把重组项删掉并投递。于是：

    第一份副本 -> 建项 -> 收全 -> 删项 -> 执行处理器
    重复副本   -> 没有项 -> 建新项 -> 收全 -> 删项 -> 再执行一次

而心跳这类请求恰好都是单分片。也就是说，UDP 上一个重复的数据报会让处理器跑两遍。
心跳是幂等的所以看不出来，但"同一事务至多执行一次"这条不变量已经不成立。

## 2. 修法

在 Mux 里加一个有界的"已完成事务"集合：

| 细节 | 取值 |
|---|---|
| 容量 | 1024 条（completedHistory） |
| 淘汰 | 先进先出，只留最近完成的 |
| 检查时机 | 建重组项之前 |

选环形淘汰而不是时间窗，是为了让内存占用与对端行为无关。

## 3. 证据

TestCompletedTransactionIsNotMergedTwice：同一事务喂两次则只投递一次；
再用不同事务喂一次则正常投递（确认不是"把所有东西都挡掉"）。

探针（去掉检查）：

    a retransmitted request was delivered a second time

## 5. 判断

这条缺陷有意思的地方在于：**它在 TCP 上几乎不可能出现**（流式传输不会重复交付单帧），
所以它从项目第一天起就存在，却一直无害。是我自己把 UDP 接进来之后，它才变成真的。

这轮的价值不在代码，而在于那行"没找的"——上一轮如果含糊地写"已全面覆盖"，这一轮就不会去看它。

## 6. 补记：我第一版修错了，被门禁抓了回来

第一版去重只按 transaction id 做键。它让新用例变绿，但门禁立刻红了两处：

    --- FAIL: TestProxyRPCListRouteEndToEnd
        list_route = 500 internal error
    == postgres deploy  FAIL
        the member override never reached the device

原因是：**事务 id 只在单个 mux 内唯一**。同一进程里不同对端（或同一对端新建的 mux）
会各自从 1 开始编号，服务端按 id 去重就会把它们当成重复请求直接丢掉。

改成"对端 + 事务 id + 载荷长度 + 2 秒窗口"之后两处都恢复。
真正的重传是毫秒级、同对端、同载荷；合法复用 id 不会被吞。

这条值得单独写进来：**我的修复本身制造了一个更严重的缺陷（合法请求被静默丢弃）**，
而抓到它的不是我的自测，是既有的两条用例。如果没有那两条用例，
这个去重会以"看起来更安全"的样子活着。
