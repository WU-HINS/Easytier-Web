# 第 69 轮评审（2026-11-01）— 覆盖配置真的会到设备吗

r68 把"成员覆盖配置"接到了界面。但**界面能改**不等于**改完有用**：compile 层有 golden 用例，
httpapi 有接口用例，可是"PUT 覆盖 → 对账 → 设备收到 mtu=1300"这条完整链路没人走过。

## 1. F-124（P2）补齐端到端

给假设备加上 mtu 上报（`CONFIG_RECEIVED ... mtu=1300`），冒烟在成员重命名之后 PUT 一份覆盖：

```json
{"override_config":"{\"mtu\":1300}"}
```

设备收到的第二条配置随之变成 `mtu=1300`，脚本断言该字符串存在：

```
member override set            204
member override read           {"override_config":"{\"mtu\":1300}"}
configs received               ... hostname=smoke-device mtu=0 | ... hostname=smoke-renamed mtu=1300
override applied on device     mtu=1300
```

负向自测：把期望值改成 `mtu=1400`，立刻 `FAIL: the member override never reached the device`。**这条断言确实会红。**

## 2. F-125（P2）我把冒烟改坏了三次

这轮真正的教训在这里：

| 次数 | 我做了什么 | 结果 |
|---|---|---|
| 1 | 在 python 里拼带反斜杠的 JSON 交给 `curl -d` | 反斜杠被模板吃掉 → PUT 返回 **400** |
| 2 | 把断言用字符串替换插进脚本 | 插进了 `$( ... )` 的中间，`step` 输出变成一串竖线加 w，**断言从未执行** |
| 3 | 第一次"跑通" | 其实是断言没跑，不是功能正常 |

三条修正：

1. JSON 用 heredoc 写进文件，`curl -d @file`，不再拼转义；
2. 断言按**整行重建**，不做子串插入；
3. 每次改完跑一次"故意改错期望值"的负向自测，确认断言真的会红。

第 3 条是关键：**一个不执行的断言，和一个永远通过的断言，是同一种东西。**

## 3. 顺便重排队列

冒烟从"重命名 + 覆盖"两次变更里只看到 **2 条**配置（不是 3 条）——因为设备是在两次变更都完成后才接入的，
对账只推最终态。这和 r65 的发现一致：**修订未变不重复下发**。
