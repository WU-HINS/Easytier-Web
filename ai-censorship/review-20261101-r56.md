# 第 56 轮评审（2026-11-01）— 踢人要当下生效

顺着 r55 补的"阻止接入"继续往下看：**阻止之后，正在连接的设备会怎样？**

## 1. F-112（P1）阻止只拦住"下一次"，拦不住"现在"

心跳路径里的判断是：

```go
if !bound {
    userID, err := m.auth.AuthenticateToken(ctx, req.UserToken, machineID)
    if errors.Is(err, ErrBlocked) {
        return nil, fmt.Errorf("session: device %s is blocked", machineID)
    }
    ...
}
```

`!bound` 意味着**只有第一次心跳会做认证**。已经连上的设备被管理员阻止后，
它的会话还在、隧道还在、还能下发配置——直到它自己重连（可能是几天后，也可能是永不）。

这跟 r48 记的"禁用账户不影响已登录会话"是同一个形状，但严重性不同：

- 禁用账户：那人下一次登录进不来，影响面有限；
- 阻止设备：管理员以为"这台机器已经被踢出去了"，而它还在网络里。

## 2. 修复：阻止 → 立即断开

`Manager.DisconnectDevice(userID, machineID)`：按 (租户, 机器) 找到会话，关掉 mux 并从表里摘除
（和 `DisconnectUser` 同一套做法，只是粒度到机器）。

`handleDeleteMachine` 在 `BlockDevice` 成功后立即调用它。

`TestBlockingDisconnectsLiveDevice`：

| 步骤 | 断言 |
|---|---|
| 设备连上并心跳 | 会话数 = 1 |
| `DELETE /machines/{id}?block=true` | 204 |
| 立刻检查会话 | **0**（不用等下一次心跳） |
| 同一设备再连一次 | 心跳被拒 |

## 3. 过程中的一个测试陷阱

第一版用例跑了 **30 秒**。原因是我的 listen goroutine 只 `Accept` 一次，第二次 dial 在 TCP 层
能连上但没人 `Serve`，于是客户端的 `Call` 一直等到 ctx 超时——**测试通过但慢得离谱**。
改成循环 Accept 后 0.65 秒。

记下来的理由：**通过但慢的测试**会被人当噪音，最后被跳过；它和失败的测试一样危险。

## 5. 判断

"撤销"这个动作在这套系统里有三个层次，现在都有明确的语义与用例：

| 动作 | 语义 | 生效时机 |
|---|---|---|
| 删除成员 | 设备不再收到该网络的配置，实例被收回 | 下一轮对账（≤5s，r38） |
| 阻止设备 | 拒绝接入 + 立即断开现有会话 | **立即**（本轮） |
| 禁用账户 | 不再允许登录 | 下一次登录（r48，有意如此） |

三者语义不同是有原因的，但**必须写下来**，否则下次有人会以为是 bug。
