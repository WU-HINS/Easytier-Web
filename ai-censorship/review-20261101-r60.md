# 第 60 轮评审（2026-11-01）— 前端的单一出口

r58/r59 讲的是"守卫不该依赖人工清单"。本轮把这套标准用在前端：**有没有哪条约定，是靠人自觉遵守的？**

## 1. F-116（P2）谁都可以直接 fetch

`client/src/lib/http.ts` 是所有请求的唯一入口，它负责三件事：

| 职责 | 如果绕过它 |
|---|---|
| `credentials: 'same-origin'` | 请求可能不带 cookie，行为随浏览器而异 |
| 统一的错误映射（`ApiError + message`） | 组件里出现裸 `response.statusText` |
| 与后端 CSRF 校验配套的同源语义 | 用错头，被服务端 403 而不知道为什么 |

目前全仓只有一处 `fetch(`（就在 http.ts 里）——但这是**巧合还是约定**？没有任何东西保证下一个组件不会
在 200 行里顺手写一句 `await fetch('/api/v1/...')`。一旦发生，它仍然能跑通，
只是悄悄绕过了上面三条。

同类的还有 `dangerouslySetInnerHTML`：当前一处都没有，但没有守卫意味着
"引入一个富文本提示"就可能变成 XSS 面。

## 2. 两条新规则（在已有的 ui states 里）

1. **除 `client/src/lib/http.ts` 外，出现 `fetch(` 即失败**。
   按标识符边界匹配（前一字符不是字母数字下划线），所以 `refetch(`、`prefetch(` 不会误报。
2. **出现 `dangerouslySetInnerHTML` 即失败**。需要时应当显式评审，而不是顺手写。

## 3. 自测

放一个临时组件：

```tsx
export function Probe() {
  void fetch('/api/v1/console-info');
  return <div dangerouslySetInnerHTML={{ __html: '<b>x</b>' }} />;
}
```

```
ui: 2 problem(s)
  features/tmpprobe.tsx:2 calls fetch() directly; use lib/http.ts
  features/tmpprobe.tsx:3 uses dangerouslySetInnerHTML
```

删除后恢复绿。
