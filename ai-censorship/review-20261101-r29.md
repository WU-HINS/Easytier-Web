# 第 29 轮评审（2026-11-01）— override 语义与下发前校验

继续用"对照上游"的方法，本轮看 `apply_member_override` 与 `validate_member_config`。

## 1. F-068 覆盖配置能不能改写受保护字段？—— 不能，但以前没证据

上游 `apply_member_override` 在合并后会**强制还原**受保护字段：

```rust
merged.network_secret = base.network_secret;
merged.networking_method = base.networking_method;
merged.public_server_url = base.public_server_url;
merged.peer_urls = base.peer_urls;
merged.secure_mode = base.secure_mode;
merged.managed_credentials = base.managed_credentials;
merged.acl = base.acl;
```

我们的实现不是"合并后还原"，而是 `Overrides` **白名单结构体**：只解析 10 个允许的字段，
未知键被 `json.Unmarshal` 直接丢弃。安全性等价（甚至更强），但**没有任何用例证明过**。

新增 `TestOverrideCannotTouchProtectedFields`：塞进
`network_secret / network_name / peer_urls / managed_credentials / virtual_ipv4 / acl`
六个敌意键，断言编译结果里这些字段全部保持原样，同时白名单的 `no_tun` / `mtu` 正常生效。

结论：**没有缺陷**，但这条防线现在有证据了。

## 2. F-067 下发前没有结构校验

上游在生成配置后会跑一遍 `CoreInstanceConfig::from_toml(config.gen_config())`，
组合非法直接编译失败。我们什么都不校验：`proxy_cidrs` 写错、`listener_urls` 少端口、
`mtu` 写成 64——全都会被推给设备，设备侧实例起不来，控制台只看到
`reconcile failed`，用户完全不知道错在哪。

**修复**：`validateCompiledConfig` 在 `buildConfig` 末尾校验

- `network_name` 非空、`instance_id` 是 UUID；
- 虚拟地址是 IPv4 且前缀在 0..32；
- `proxy_cidrs` 能解析成 CIDR；
- `listener_urls` / `peer_urls` 有支持的 scheme、host 与端口；
- `mtu` 在 576..65535。

**回归** `TestCompileRejectsBrokenConfigs`（4 类非法输入各断言错误文案要点）与
`TestCompileRejectsInvalidNetworkName`。

## 3. 与上游的差异（已知且有意）

我们不做 `gen_config()` + TOML 往返，因为那需要把整个核心配置模型搬过来。当前选择是
**结构级校验 + 明确错误文案**，而不是完整的核心语义校验。这条差异写在这里，避免以后误以为已经等价。
