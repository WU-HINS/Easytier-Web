# 第 92 轮评审（2026-11-01）— 一条从来没看过东西的守卫

r91 把前端的行为规则搬进了门禁。这轮顺手检查 r60 加的那条老规则：
**"fetch 只能出现在 `lib/http.ts`"**——它到底扫过什么？

答案是：**什么都没扫过。**

## 1. F-156（P1）三重空转

| 环节 | 实际行为 |
|---|---|
| `walk()` | 只收集 `.tsx`，不收集 `.ts` |
| `extraSources` | 从 `files`（全是 tsx）里再筛 `.ts` —— 恒为空 |
| 跳过条件 | 写的是 `./lib/http.ts`，而实际路径是 `lib/http.ts` —— 永远不相等 |

三个错误叠在一起，结果就是：这条规则**从加进去那天起就没有检查过任何一个 .ts 文件**。
谁在 `lib/` 里再写一个 `fetch` 都不会被发现。

这不是"规则太严"，是"规则不存在"——而门禁一直显示 PASS。

## 2. 修法

- 新增独立的 `.ts` 遍历（`moduleFiles`），fetch 规则扫描 `.tsx + .ts`；
- 跳过点改成真实的 `lib/request.ts`（本轮新增的唯一允许点）。

自测：在 `lib/origin.ts` 里写一行 `fetch`，立刻报

    lib/origin.ts:31 calls fetch() directly; use lib/request.ts

## 3. F-157（P2）顺手把传输契约钉住

修这条规则时发现 `request()` 本身也没有任何验证。它是所有页面共同依赖的东西：

| 行为 | 为什么重要 |
|---|---|
| `credentials: same-origin` | 少了它，所有请求都不带 cookie，全站 401 |
| JSON 里的 `message` 优先 | 后端就是这么表达 `setup_required` / `quota_exceeded` 的 |
| 非 JSON 回落到 `statusText` | 反向代理的 502 往往是 HTML |
| `204` 不解析 body | 加成员、解绑都用 204，解析会抛异常 |
| 调用方 header 覆盖默认 | 否则将来加不了别的 Content-Type |

为此把 `ApiError` 与 `request()` 抽到无依赖的 `client/src/lib/request.ts`（`http.ts` 只 re-export），
新增门禁第 19 项，用 stub 的 `fetch` 逐条验证。

## 6. 判断

这轮的 P1 不是产品缺陷，而是**门禁自己在骗人**。它比产品缺陷更值得记：
一条永远为真的断言，比没有断言更糟——因为它让人以为有。

这也解释了为什么每轮都要做负向自测：**能红的断言才算断言**。
