# 第 13 轮评审（2026-11-01）— WebSocket 接入面

r12 收尾时留了一句"WS 面只做过读上限"。本轮把它补齐，同时第一次**端到端**验证
"实例与面板共用端口、注册在 `/@up/<用户名>`" 这个需求。

## 1. 首次端到端验证（此前从未跑过）

`TestWSUploadChannelCarriesHeartbeat`：用 gorilla 客户端连 `ws://host/@up/wsuser`，
走真实心跳，随后断言：会话注册且 online、hostname 正确、**设备行已落库**。
在此之前所有会话测试走的都是 TCP 控制面，WS 路径属于"写了但没验过"。

同时验证：路径用户名与心跳 token 不一致会被拒绝（`TestWSUploadRejectsBadPathIdentity`）。

## 2. F-032（P2）错路径返回 200 HTML

`/@up`、`/@up/`（漏写用户名）落到 SPA 兜底，返回 **200 + index.html**。
对设备管理器来说这是一次"握手失败但服务端 200"，运维在设备日志里看到 200 会把矛头指向客户端；
线上还出现过这种路径被 CDN 缓存成静态页的情况。

**修复**：显式注册两个路径返回 400 JSON。线上实拍：

```
/@up/        400 {"message":"device upload path must be /@up/<username>"}
/@up         400 {"message":"device upload path must be /@up/<username>"}
/@up/alice   400 Bad Request        (没有 Upgrade 头)
```

## 3. F-033（P2）上传通道无并发上限

`handleDeviceWS` 在 handler goroutine 里同步跑 `ServeAs`，没有任何并发闸门。
r12 加的空闲看门狗只是"延迟释放"，不是"限制数量"：攻击者可以在 15 秒窗口内堆几千条半开连接。

**修复**：信号量上限 1024（`Config.MaxUploadConns` 可调），超限直接 503 + `Retry-After: 5`。
**回归** `TestWSUploadConcurrencyIsBounded`：上限设 2，第三条 dial 拿到 503。

## 4. F-034（P2）门禁自身会抖

新增的超大帧用例首版断言写死"写 2MB 必须成功、随后的读必须失败"。实际服务端在读到超限时会
**直接 RST**，客户端 write 因此报错——脚本把它当成失败，门禁随机 FAIL（5 次里 3 次）。

这是**测试的问题，不是产品的问题**：服务端提前切断连接是正确行为。断言改为
"write 与 read 不得同时成功"，连跑 6 次 + 完整门禁连跑 2 次全绿。

**为什么记进台账**：门禁不稳定比没有门禁更糟——它会让团队习惯性地"重跑一次"，
从而对真正的红灯脱敏。
